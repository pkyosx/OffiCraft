# server/ — Go server daemon (ocserverd)

進入 `server/` 時 nested-load。repo-wide 憲章 + 約定見 root `CLAUDE.md`;本檔記 server 專屬。棧:go1.26。

## 命名(root §10)
- **`server/ocserverd/`** — Go server daemon(**production server**;原 Python 實作已退役——歷史 = git tag `py-final`)。folder = `module ocserverd` = binary `ocserverd`。`ocserverd` 由 `go build` fresh 產出、**永不 commit**(OffiCraft policy:零 committed binary——CI step 1 build fresh、無本地 prebuilt 就 skip parity;此 gate 迴圈自動納入 `server/*/go.mod`)。⚠️ 別跟 `bin/ocserver`(bash 的 server *installer*)混淆——`d` 是 daemon 本體。
- (已拆除,t-dc68)`server/ocupdaterd/`(發佈/更新伺服器)與 `cli/ocrelease/`(發佈客戶端)整組退役:發佈改走 **GitHub Releases(repo pkyosx/OffiCraft)**——`bin/release <tag>` 從 clean HEAD 打包 `officraft-<tag>-darwin-arm64.tar.gz` + `checksums.txt`(sha256),出貨 = 顯式 `gh release create`。下游更新檢查/升級由 ocserverd 自己對 GitHub API 做(見下方「軟體更新檢查 + 升級」)。邀請碼/publish token/beta-GA promote/portal/fleet 監控等概念隨之作廢(Beta = GitHub prerelease)。歷史實作見 git(t-dc68 前)。

owner 原話:「我建議所有換手都可以給他機會收尾」。**relocate(改機器)/ restart(重啟)/ 換 model 三個動詞原本是直接砍掉重起**——無 `refocus_since` stamp、無 SOP 預告、無寬限,前一輪在途的東西沒有機會落盤;而 **換手(refocus)自 T-ea82 起就有完整的 預告→寬限→收口**。從 worker 的角度這四件事是同一件事(這個 session 結束、下一個接著做同一個任務),沒有理由厚此薄彼。

- **改動點只有一處**:`respawnWorkerForOwnerOp`(三個動詞唯一的漏斗)在既有的 `desired_state==offline → held_down` 分流**之後**多一道分流,走 `openOwnerOpHandover`(stamp 新的 refocus epoch + `openWorkerHandoverGrace` 預告,**不砍**)。收口沿用既有的兩個 driver:worker 自己的 `report_stopped`,或 `autoHandoverWorker` in-flight 臂的 `StoppingTimeoutSecs` 天花板。**新的 pin / model 在開窗前就已經寫進 row**,所以收口那次 respawn 自然帶上新值。原本的立即路徑原封不動搬進 `respawnWorkerForOwnerOpNow`。
- 🔴 **「有東西要存才等,沒有就立刻走」的判準(owner 在意體感:不要改個模型乾等 120 秒)**。server 能**證明**的「沒東西要存」有下列幾種,每一種都是結構事實不是猜測(前兩條是原始的兩種,3./4. 是兩輪獨立審查各補的一種,5. 是 deny-list 例外):
  1. **沒有活 session**(`!hub.IsOnline`)——沒有東西聽得到預告、也沒有東西能存。這是 `openWorkerHandoverGrace` 早就有的 D6 規則。
  2. **從沒認領任務**(`Status != active`,即 `activated_ts == 0`)——assigned→active 的翻轉**就是** `get_my_task` 那一次認領,所以非 active 的 session **可證明**從沒拿到任務內容,沒有任務狀態可回寫。
  3. **這個 epoch 的收尾已經收攏**(`refocus_since > 0` **且** `stopped_since > 0`)——收口 latch 代表 kill+start 已經用**當時**的 model/machine 派出去了,舊 session 只是還沒被 warden 收屍,所以沒有東西還要 flush,動詞必須**立刻**派。🔴 **兩個條件缺一不可,而且是兩輪獨立審查各抓一次的同一個判斷式**:少了 `stopped_since` 那半 = 第一輪的 HIGH(收攏窗內的動詞被靜默丟棄);少了 `refocus_since` 那半 = 第二輪的 HIGH(見下條)。
  4. 🔴 **`stopped_since` 有兩個 latch 點,只有一個是換手——所以判準一定要 epoch-scoped**:`collectWorkerHandover` latch 它當作某個 refocus epoch 的收口,但 `workerReportStopped` 的 **else 臂**也會 latch 它,那是**換手之外**的一次普通「停止 → worker 回報自己收工了」。**沒有任何東西會清掉後者**——`clearWorkerRefocus` 只在 `refocus_since > 0` 時可達,重啟 handler 只寫 `desired_state`——所以那個 latch 會活過整個 停止→重啟 循環。拿**全域**的 `stopped_since` 去讀,它就永遠在說「已經收攏了」:那個 worker **從此每一次** 改機器／換 model 都被當場砍掉,無預告、無寬限、未存的東西全丟,而且**一直重複**。這比第一輪那個窗口洞更廣也更日常。配上 `refocus_since > 0` 才是原本要問的問題(**這個 epoch** 收攏了嗎)——收口只可能屬於某個 epoch。殘留 latch 隨後自癒:下一次開窗(`openOwnerOpHandover`)會把它歸零。
  5. **另外一個 deny-list 例外:`restart`**(`ownerOpRevivesStoppedWorker`)——重啟只會在 `desired_state` 剛從 offline 翻回 online 時走到這裡,它要取代的那個 session **是 停止 已經下過殺令的**;對它 fan 預告然後等滿一輪,等的是一個永遠不會來的回答。**刻意做成 deny-list 而非 allow-list**:之後新增的動詞預設**有**收尾,「不給」才需要被論證。
- ⚠️ **active + online 那一格是誠實的退路,不是正向偵測**:server 對 agent 的 transcript **零可見度**,唯一知道「有沒有東西還沒存」的是 agent 自己。再細的 server 端判準(context pct、開機多久、訊息數)都是**把猜測包裝成判準**,猜錯的代價是那一輪的 learnings 無聲全掉。所以這一格走 **「照舊等滿但可提早結束」**:`StoppingTimeoutSecs` 只是**天花板不是時長**,收口在 worker 回 `report_stopped` 的那一刻就發生——沒東西要存的 session 幾秒就結束。
- **agent 互動面零改動**(§9c 檢查過):fan 出去的還是同一則 member-topic delta,ocagent 的 recycleHook refetch 後印同一份五步 SOP。沒有新工具、沒有新步驟,所以 `seeds/` 不需要同批改。

## 累積型 context 文件的硬上限(T-3351,`domain.go DocCapBlocked`)

owner 2026-07-27 兩句話 + 一個數字:「更新的時候不能塞超過這個大小」「已經超出的我們不 truncate 但是下次更新他只能縮小」,上限 **10,000**。

- **單位是 rune,不是 byte**(`utf8.RuneCountInString`,對齊 `chatBodyMaxChars` 的口徑)。owner 挑 10,000 時看的分佈是 SQLite `length()`=**字元**;這些文件多為中文散文(2.2–3 bytes/字),拿 `len()` 當上限實際只剩約 3,300–4,500 個中文字,**比 owner 拍板的數字嚴格一倍以上**。⚠️ patch receipt 的 `size` 欄仍是 `len()`=**bytes**(凍結 wire 欄,不動),兩者單位不同是刻意的——所以拒絕訊息一律講 "chars"。
- **三行語意(邊界含在內)**:新內容 ≤ L → 過;> L 且 **< 舊內容** → 過(允許超標者繼續往下縮);> L 且 **≥ 舊內容** → 拒,**含等長**(沒變短就不算收斂,不然超標文件可以永遠整份重寫)。**既有超標內容一律不動、不截斷**——這條規則只擋 WRITE。第一次寫(無舊內容)只看 ≤ L。
- **比的是「caller 讀到、正在編輯的那份」**:lessons 用 `foldLessonsDTO` 的 overlay ⊕ seed 折疊結果,手冊用存的欄位。**刻意與 `LessonsShrinkBlocked` 用同一個 `before`**,兩道閘因此不可能對「現在的文件是什麼」各說各話。(`seeds/lessons.md` 實測 **40 bytes = 14 runes**——這張票的主旨就是 rune≠byte,所以兩個單位都寫明、不含糊講「字元」;不論用哪個尺都遠小於 L,所以 seed role 的第一次寫實務上就是「只看 ≤ L」,fold-vs-overlay 在現行 seed 大小下行為不可區分。)
- **五個寫入面全覆蓋**:`replace_lessons` / `patch_lessons` / `write_task_learnings` / `patch_task_learnings` / **`update_task_manual`**。最後一個非補不可:它是 `sop_md` 的**唯一**寫入面,也是 learnings 的**第二個**寫入面(欄名 `learnings`,與 `write_task_learnings` 的 `text` 是同一份文件)——只擋前四個等於留一扇沒上鎖的門。**patch 面受檢的是「改完之後的結果」,不是 patch 自己的大小**(小 patch 疊上大文件正是把它撐大的東西)。
- **與 `allow_shrink` 的關係:兩道閘方向相反、並存、互不代勞**。`allow_shrink` 擋的是「縮太多」(整份清空 / 縮到不到十分之一),這道擋的是「太大且沒變短」。**`allow_shrink=true` 不是本閘的旁路,本閘無條件檢查**;拒絕訊息也**刻意不提任何參數**——這是 fail-closed 閘,教人繞過等於把 owner 拍板的上限做成裝飾。⚠️ 兩者**不是「由構造互斥」**(此處原本這麼寫,是錯的):`LessonsShrinkBlocked` 的 `TrimSpace(after)==""` 那一臂**沒有長度上界**,所以 `before` = 20,000 個 `a`、`after` = 25,000 個空白會被**兩道閘同時擋**(實測 2026-07-27:cap=true、shrink=true)。**但不會讓任何人無路可走**:重疊區**只有「新內容 trim 後全為空白」這一種**,而那本來就該被擋——它不是「往下收斂」,是清空。**after trim 後非空白時,兩閘確實互斥,而且可證**:shrink guard 要 `len(after)*10 < len(before)`(bytes),本閘要 `runes(after) ≥ runes(before)`;UTF-8 下 `runes ≤ bytes ≤ 4×runes`,由前式得 `runes(after) ≤ bytes(after) < bytes(before)/10 ≤ 0.4×runes(before) < runes(before)`,與後式矛盾。單位不同也不破(兩閘一個是 byte 一個是 rune)。實測掃過 100 組隨機非空白配對 + ~19 萬組網格配對,零反例。(43k → 4k 走 `allow_shrink`;43k → 40k 兩閘都不擋。)
- 🔴 **「超標但變短」這條路一定會被用到**:立案時正式站有 **2 份 lessons**(43,029 / 12,132)與 **4 份 manual learnings**(19,336 / 14,691 / 11,031 / 10,557)已超標(sop_md 全數在界內,最大 3,546)。掉了這條,那六份文件**永遠改不了,連想變短都不行**。

## 每位成員的個人圖片頭像(T-c826)

- 個人圖以 stable member id 綁在 `member.avatar_attachment_id`，圖片 bytes 重用
  `chat_attachment`，但 id 使用專用 `ava-` 前綴。顯示鏈固定為「個人圖 →
  role/theme 圖 → glyph」，不以 display name 當 key，也不在 Avatar 上畫 presence。
- `PUT/DELETE /api/members/{member_id}/avatar` 由 owner 2026-07-27 明確裁定
  `requires=owner` 且 `MCPExclude`；外包與正職共用 member row，warden/machine
  目標一律 422。PUT 只收原始 PNG/JPEG/WEBP、最多 64 KiB，server 以 magic bytes
  驗證，不能只信瀏覽器 MIME。
- replacement、remove、hard delete 與 migration rollback 都必須在同一 transaction
  內維護 pointer/blob，不得留下舊 blob 或懸空 pointer。每次 replacement mint 新
  `ava-` id，自然 cache-bust。staff 發既有 `member` delta，外包發
  `outsource_worker` delta；SSE 永不攜帶圖片 bytes。
- `ava-` blob 是 single-owner，chat/reply/task attachment ref 與 task artifact
  一律拒收，避免 replacement/remove 讓一般紀錄懸空。一般 `PutMember` conflict
  update 也不得寫 `avatar_attachment_id`；只有專用 avatar mutator 可改該 pointer，
  避免 stale lifecycle/model snapshot 洗掉較新的頭像。
## activity — 「有沒有在跑 turn」是第二個維度(T-a1d7)

權威 logical spec:`docs/design/activity-model.md`。這裡只記 server 面的落點與三個容易踩的點。

- **第三個記憶體 store `s.activity`**(`api_activity.go`),與 telemetry / gauge 同型別但**刻意分開**:telemetry 的公開契約是「解僱才清、**斷線不清**」,activity 需要斷線邊——共用會把那句話變成「看情況」。volatile 是契約,重啟後全部誠實回到 `never`。
- **裁決只有一個地方**:`domain.go` 的純函數 `deriveActivity`,同時餵 `monitoringSessionDTO` 與 `outsourceWorkerDTO`(「一個推導函數、兩條 wire」,與 `foldActorRuntime` 同形)。⚠️ **不塞進 `deriveLiveness`**——presence 與 activity 是不同問題,合併詞彙就會讓「離線」和「沒在工作」變成同一個字。
- ⚠️ **兩個門檻是兩個量,別互換**:`activityMaxTurnSecs`(2700s,owner `rc-3b18366fbe04` 拍板)問的是「還 online 但這輪沒送結束訊號,多久後停止宣稱工作中」;`reconcileCfg.ZombieConfirmGrace`(180s)問的是「連線斷多久才算真的離開」,activity 在**重連邊**原樣沿用它、不另造數字。
- **斷線不刪主張、也不蓋 `last_end`**:`onLastDisconnect` 只記 `offline_since`,顯示面靠 `deriveActivity` 對 `online` 的 gate 擋住「離線卻說工作中」。理由是 `ocagent listen` 的 drop→reconnect 是常態,刪掉的主張這一輪救不回來(Claude 要到 turn 結束才會再說話);而把斷線寫成「結束時刻」是捏造一個沒觀察到的事實。
- **`POST /api/self/activity` 是 `requires=agent` + `MCPExclude`**:比 `/api/self/*` 其他列高一階,因為它**不解析 member row**(外包 `ow-` 必須能用,同 `GET /api/self/task`);不出 MCP 工具是決定不是遺漏——出了就是邀請 agent 手寫自己的活動狀態。

## 慣例
- 改 Go → fresh build 驗證，**不 commit binary**(root §13)。需要可單檔 boot/裝機的 build 前，先跑 `bash bin/build-seedsdist && bash bin/build-bindist` 再 `go build -ldflags="-s -w"`——asset 已 embed-only，漏 staging 會默默丟掉單檔 boot/裝機能力；本機產物是 gitignored，部署 binary 由發版流程 fresh build，parity dryrun 的 `--help` 對比抓不到內容面漏 staging，故此步靠人工紀律。
- 有別於 cli/ 的 stdlib-only:本模組帶第三方依賴(BurntSushi/toml、pressly/goose/v3、modernc.org/sqlite)——server 端 schema/config 需求正當化;新增依賴前先想能不能 stdlib。
- 新端點 = RouteSpec 表加一行(`routes.go`),不散寫 mount;boot assertion 缺 requires 即拒起。
