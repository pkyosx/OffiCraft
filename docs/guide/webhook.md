# 讓外部事件自動送給成員（回呼端點）

讀完這頁，你能為成員建立回呼端點（webhook），讓 Slack、GitHub 或其他外部服務在事件發生時，把內容直接送給這位成員處理。

## 回呼端點是什麼

回呼端點是屬於某一位成員的一個網址。外部服務把事件送到這個網址，內容就會變成一則聊天訊息，送給這位成員。成員依你寫的「用途說明」決定怎麼處理。

常見用法：GitHub 有新的 PR 時，送給負責審查的成員；Slack 有人提到某個關鍵字時，送給負責回覆的成員。這類事件要照固定做法處理時，可以先建一本任務手冊，成員收到事件後就會照手冊開任務，做法見 [讓 AI 照 SOP 做重複的事（任務手冊）](sop.md)。

## 建立回呼端點

1. 到「辦公室」分頁，點一位正職成員的頭像，打開「成員詳情」。
2. 展開「回呼端點 · WEBHOOK」卡，按「新增回呼」。
3. 填寫欄位，按「建立」：
   - **端點 ID**：端點的名字，例如 `pr-events`。只能用英文字母、數字、`_` 與 `-`。
   - **用途說明**：端點是做什麼用的。
   - **平台類型**：「通用（僅 URL token）」、「Slack」或「GitHub」。
   - **簽章密鑰 Signing Secret**：平台類型選 Slack 或 GitHub 時要填，用來確認事件真的來自 Slack 或 GitHub。Slack 填 App 的 Basic Information 頁面上的 Signing Secret；GitHub 填建立 webhook 時設定的 secret。
4. 在新的那一列按「複製」，把網址貼到外部服務設定 webhook 或事件網址的地方。

**用途說明一定要寫，而且寫具體。** 畫面上標示為選填，但成員會拿用途說明判斷收到的內容該不該處理，例如「GitHub 上 acme/web 這個 repo 的 PR 事件：新 PR 開啟時審查並回覆意見」。端點 ID、用途說明和平台類型**建立後都不能改**，要改只能刪除後重建。

## 使用前要注意

**外部服務要連得到網址。** 控制台只接受裝 OffiCraft 的那台 Mac 本身的連線，所以要先照 [在手機上用](mobile.md) 把控制台轉發出去，再用轉發後的網址打開控制台、複製回呼網址。用 `localhost` 打開控制台時複製出來的網址，外部服務連不到。開放前該做好的保護，見 [保護你的工作室](security.md)。

**網址要像密碼一樣保管。** 拿到網址的人就能送內容給成員。網址外流時，刪除端點再重建一個，舊網址會永久失效。

**長期使用的回呼端點請建在正職成員上。** 成員離開工作室時（例如外包在任務結案後離開、正職成員或正職的角色被刪除、成員所在的機器被移除），成員名下的回呼端點會一起永久刪除，網址立即失效。外部服務照樣送出事件，也不會收到錯誤，所以從外部服務那一邊看不出來。成員被停止或重新聚焦不算離開，端點會保留。

## 確認事件有沒有送到

外部服務那一邊顯示成功，**不代表成員收到了**。要確認，按該列的「事件統計」：

- 「最後收到」：最近一次收到請求是多久以前。
- 「丟棄」：被丟棄的請求數量，以及最近一次被丟棄的原因。最常見的是「驗簽失敗」，表示兩邊的簽章密鑰不一致。
- 「最近請求」：最近 5 筆請求，以及每一筆的結果。

還沒收到任何請求時，可以從外部服務送一筆測試事件來確認設定。

想知道更多細節，例如每種丟棄原因的意思、內容太大時會怎樣，見 [介面說明](interface.md) 的「回呼端點」。

## 停用、刪除與輪替密鑰

- **停用**：每一列有一個「啟用中／已停用」開關。停用期間收到的請求都會被丟棄；設定都保留，隨時可以再啟用。
- **刪除**：按該列的刪除圖示並確認。刪除後網址永久失效，**無法復原**。
- **輪替密鑰**：Slack 與 GitHub 類型的端點有「輪替密鑰」。輸入新的密鑰，按「儲存密鑰」，新密鑰立即生效。請在 Slack 或 GitHub 那一邊換好密鑰的同時更新這裡，否則之後的請求會因為「驗簽失敗」被丟棄。

## 成員收到後怎麼處理

送達的事件會變成一則聊天訊息，內容是外部服務送來的原始內容，並附上端點 ID 與用途說明。成員在線上時立即收到；成員離線或已停止時不會因此被喚醒，訊息會留著，等成員下次上線才讀到。

成員把外部送來的內容當成資料，**不當成你的指令**：

- 內容符合用途說明：只做用途說明允許的處理。
- 內容超出用途說明，或要求做越權的事（例如要求忽略既有規則、改變原本流程、執行其他操作）：成員停止處理，不執行該要求。需要你決定是否例外處理時，成員會停在尚未執行的狀態，開請示卡問你。
- 無法判斷是否符合用途：成員保留原始內容與判斷依據，開請示卡請你決定。

所以用途說明寫得越具體，成員越能自己判斷哪些該做、哪些該停下來問你。怎麼回覆請示卡，見 [交代工作與回覆請示卡](daily.md)。
