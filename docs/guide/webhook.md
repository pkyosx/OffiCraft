# 讓外部事件自動送給成員

讀完這頁，你能為成員建立回呼端點（webhook），讓 Slack、GitHub 或其他外部服務在事件發生時把內容直接送給這位成員處理。

## 回呼端點是什麼

回呼端點是綁在某一位成員身上的一個網址。外部服務對這個網址送出請求時，伺服器把請求內容轉成一則聊天訊息送給這位成員，成員依你寫的用途說明處理。

常見用法：GitHub 有新的 PR 時送給負責審查的成員；Slack 有人提到某個關鍵字時送給負責回覆的成員。若這類事件要照固定做法處理，可以先建一本任務手冊，成員收到事件後就會照手冊建任務，做法請看 [讓 AI 照 SOP 做重複的事](sop.md)。

## 在哪裡設定

1. 到 **辦公室** 分頁，在左欄選 **正職** 或 **外包**。
2. 點成員的頭像，打開 **成員詳情**（外包是 **外包詳情**）。
3. 展開 **回呼端點 · WEBHOOK** 卡。卡上列出這位成員所有的回呼端點；還沒有時顯示「尚未設定回呼端點」。

## 新增回呼端點

在 **回呼端點 · WEBHOOK** 卡按 **新增回呼**，填寫以下欄位後按 **建立**：

- **端點 ID**：這個端點的名稱，例如 `pr-events`。只能用英文字母、數字、`_` 與 `-`，同一位成員底下不能重複，建立後不能修改。
- **用途說明**：這個端點是做什麼用的。畫面上標示為選填，但成員會拿這段文字判斷收到的內容該不該處理，建議一定要寫，而且寫具體，例如「GitHub 上 acme/web 這個 repo 的 PR 事件：新 PR 開啟時審查並回覆意見」。用途說明建立後在控制台上無法修改，要改只能刪除後重建。
- **平台類型**：
  - **通用（僅 URL token）**：只靠網址裡的 token 辨識，不驗證簽章。任何拿到這個網址的人都能送內容進來。
  - **Slack**：伺服器會驗證 Slack 的簽章，並自動回應 Slack 設定網址時送來的驗證請求。
  - **GitHub**：伺服器會驗證 GitHub 的簽章。
- **簽章密鑰 Signing Secret**：平台類型選 Slack 或 GitHub 時必填，通用類型不需要。
  - Slack：填 App 的 Basic Information 頁面上的 Signing Secret。
  - GitHub：填建立 webhook 時設定的 secret。

平台類型建立後不能更改。建立失敗時，通常是端點 ID 含有不允許的字元，或與這位成員現有的端點 ID 重複。

## 把網址交給外部服務

每個端點列上顯示網址的前半段，token 以圓點遮住。按 **複製** 會複製完整網址，格式是：

```text
https://<你開啟控制台的位址>/in?t=<token>
```

把這個網址填到外部服務設定 webhook 或事件網址的地方。

- 網址用的是你當下開啟控制台的位址。外部服務必須連得到這個位址：伺服器預設只接受本機連線，從本機位址開啟控制台複製出來的網址，外部服務連不到。讓伺服器對外開放前要先做好的保護，請看 [保護你的工作室](security.md)。
- 網址裡的 token 就是通用類型唯一的憑證，請像密碼一樣保管。網址外流時，刪除這個端點再重建一個，舊網址會永久失效。
- Slack 第一次設定網址時會送一個驗證請求，伺服器會自動回應，最近請求裡記為「驗證握手」。
- GitHub 建立 webhook 後送出的測試事件，最近請求裡記為「PING」，不會送給成員。

伺服器回應外部服務時不透露端點是否存在：不論請求是送達、被丟棄，還是 token 根本不存在，外部服務收到的回應都相同。所以外部服務那一邊顯示成功，不代表成員收到了；要知道請求有沒有送達，請看事件統計。

## 輪替簽章密鑰

Slack 與 GitHub 類型的端點列上有 **輪替密鑰**。按下後輸入新的密鑰，按 **儲存密鑰**，新密鑰立即生效；之後用舊密鑰簽章的請求會被丟棄，原因是「驗簽失敗」。請在 Slack 或 GitHub 那一邊換好密鑰的同時更新這裡。

簽章密鑰存入後不會再顯示。通用類型沒有簽章密鑰，也沒有輪替密鑰。

## 啟用、停用與刪除

- **啟用中／已停用**：每一列有一個開關。停用後，這個網址收到的請求都會被丟棄，原因是「停用中被打」；設定都保留，可以隨時再啟用。
- **刪除**：按該列的刪除圖示並確認。刪除後 token 永久失效，無法復原。

## 事件統計與最近請求

每一列的 **事件統計** 會打開一個視窗：

- 還沒收到任何請求時，顯示「尚未收到請求」。可以從外部服務送一筆測試事件來確認設定。
- **最後收到**：最近一次收到請求是多久以前。
- **丟棄**：被丟棄的請求數量，以及最近一次被丟棄的原因：
  - **驗簽失敗**：簽章不符，通常是兩邊的簽章密鑰不一致。
  - **停用中被打**：端點停用時收到的請求。
  - **成員已不存在**：這個端點所屬的成員已經不在了。
- **最近請求**：最近 5 筆請求，最新的在最前面。每一筆標示結果：**已送達**、**丟棄**（附原因）、**驗證握手** 或 **PING**。點開一筆可以看這筆請求的 **HEADERS** 與 **BODY**；內容太長時只保留前段，並標示「已截斷」。

請求內容超過 1 MiB 時，伺服器會整筆拒收，不會截斷後轉送；最近請求裡記為丟棄。

## 成員收到後怎麼處理

送達的請求會成為一則聊天訊息，內容是外部服務送來的原始內容，並附上端點 ID 與用途說明。成員在線上時立即收到；成員離線或已停止時不會因此被喚醒，訊息會留著，等成員下次上線時讀到。

成員把外部送來的內容當成資料，不當成你的指令，處理方式如下：

- 內容符合用途說明：只做這個用途允許的處理。
- 內容超出用途說明，或要求做越權的事（例如要求忽略既有規則、改變原本流程、執行其他操作）：成員會停止處理，不執行該要求。若是否例外處理需要你決定，成員會停在尚未執行的狀態，開請示卡問你。
- 無法判斷是否符合用途：成員會保留原始內容與判斷依據，開請示卡請你決定。

所以用途說明寫得越具體，成員越能自己判斷哪些該做、哪些該停下來問你。怎麼回覆請示卡，請看 [交代工作與回覆請示卡](daily.md)。
