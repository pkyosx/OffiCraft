# 讓 AI 照 SOP 做重複的事（任務手冊）

讀完這頁，你能把一類反覆出現的工作寫成任務手冊、指定由誰負責，並寫出成員照著就能做、你事後能驗收的 SOP 與完成定義。

## 什麼時候該建任務手冊

一次性的事，直接在聊天裡交給成員。同一類請求出現第三次、你發現自己一直在重複交代同樣的做法時，就該建一本任務手冊。

任務手冊寫下一類工作的四件事：這是什麼任務、做之前需要哪些資訊、該怎麼做，以及由誰負責。建好之後，同一類的任務都照手冊做，你不必每次重講。

成員收到一件事時，會拿現有的手冊比對，判斷這件事屬於哪一類。沒有合適的手冊時，成員一樣會把事情做完，只是每次都要從頭規劃；任務卡上的任務類型會顯示「自由代辦」。

手冊寫的是這一類工作的通用做法。每一張任務實際拆成哪些步驟，由負責的成員依手冊、照那張任務的情況規劃。任務卡怎麼看，見 [追蹤任務進度](tasks.md)。

## 新增一本手冊

1. 到 **設定 › 任務手冊**，按「新增類型」。
2. 在「顯示名稱（例：審查 PR）」輸入一個好懂的名字，按「建立」。
3. 點進剛建立的手冊，點「任務定義」，依序回答三題：「這是什麼任務？」「需要哪些資訊？」「該怎麼做？」。每一題各有自己的「編輯」按鈕，可以分開改、分開存。
4. 回到手冊頁，在「負責成員」卡按「編輯」，設定這類任務由誰來做。

三題的寫法，分別見「這是什麼任務？」「需要哪些資訊？」「該怎麼做？」三節。

想知道更多細節，例如內建手冊改壞了怎麼還原、怎麼刪除手冊，見 [設定與參數](settings.md) 的「任務手冊」。

## 這是什麼任務？

這一段寫給成員看，讓成員判斷一件事該不該歸到這一類。寫清楚這類任務處理什麼工作、要達成什麼結果。容易跟其他手冊混淆時，寫出彼此的分界。

這一段只寫判斷用的資訊，做法寫在「該怎麼做？」。**這一段寫得含糊，成員就容易分錯類。**

## 需要哪些資訊？

列出做之前一定要有的資訊，每一項是一個欄位。欄位可以設成「必填」。

其中可以挑欄位設成「🔑 識別鍵」，用來防止同一件事開出兩張任務：識別鍵的值相同、而且同一類的舊任務還沒結案時，成員會沿用舊任務，不會再開一張。

**識別鍵要選「這件事是什麼」，不要選「這次從哪裡進來」。** 以審查 PR 為例，識別鍵只放 PR 連結。如果把「從哪一串 Slack 對話進來」也設成識別鍵，同一個 PR 從另一串對話被提起時，就會被當成另一件事，開出第二張任務。

識別鍵可以由好幾個欄位組成，但每個欄位都必須是「這件事是什麼」的一部分，例如「同一個 repo 的同一個版本號」。

想知道識別鍵比對的細節，例如大小寫與空白怎麼算、舊任務結案後再進來會怎樣，見 [設定與參數](settings.md) 的「任務手冊」。

## 該怎麼做？

這一段就是 SOP，也就是做這類工作的標準步驟。成員規劃任務步驟時，會以這一段為藍本。寫法建議：

- 依順序寫步驟，每一步說清楚要產出什麼。
- 寫出界線：哪些事不能做、什麼情況要先問你。
- 需要你決定或驗收的地方，直接寫明。成員規劃時會把那一步設成關卡，做到那一步就停下來等你。

SOP 存檔時會保留舊版本，改壞了可以還原，做法見 [設定與參數](settings.md) 的「版本紀錄」。

成員做事時發現 SOP 本身該改，會先開請示卡，把原文和修改後的內容並列，說明影響與理由，**等你同意後才改**。

## 設定負責成員

「負責成員」卡決定這類任務由誰來做，只有你和特助 Mira 能設定。按「編輯」後有兩種選擇：

- **指定成員**：選一位正職成員，這類任務都由這位成員負責。
- **外包**：每一張任務各找一位外包來做，任務結案後外包就離開。選外包時，要再設定 AI 執行環境、模型、投入程度、機器和雇用數量。

**選外包時一定要選機器。** 沒選機器，或選的機器離線時，外包不會開始工作，也不會改到其他機器上做。外包遲遲沒有開始時，先檢查這裡選的機器。

外包和正職的差別、雇用數量和整間工作室的外包上限怎麼設，見 [增加成員與發外包](members.md)。

## 寫好完成定義

成員規劃的每一個步驟都要寫完成定義（DoD），也就是「怎樣算做完」。沒寫完成定義的計畫送不出去；但完成定義寫得好不好，系統沒辦法檢查，要靠你在 SOP 裡引導、在驗收時把關。

好的完成定義是做完之後看得到的結果，不是要做的動作：

| 不好 | 好 |
| --- | --- |
| 跑一下測試 | 全部測試通過，且新增的三條檢查各自實測會擋 |
| 處理好 PR | PR 上留下 approve 或 request-changes 的結論 |
| 等部署完成 | 已發佈到 registry，健康檢查通過 |

判斷標準：任何人讀完這句話，都能客觀判斷有沒有做到。一個完成定義只寫一個結果；寫了兩件事，就會出現「做完一半」這種無法判定的狀態，應該拆成兩個步驟。

你可以在 SOP 裡直接寫出每一步期望的完成定義，成員規劃時就會照著寫。

## 哪些步驟該設成關卡

關卡是成員規劃時先標好、需要你決定或驗收的步驟。計畫送出時，任務卡就會在關卡上預告「等我回覆」，你一開始就知道整件事會在哪裡需要你。走到關卡時，成員會開一張請示卡，等你回覆後才繼續。

成員遵守的原則：只有需要你本人決定、核可、提供資訊或動手的事才開卡；查得到的資料、自己做得到的事，成員會自己處理。

**適合設成關卡的情況：**

- **有代價、不能回頭、或碰到風險界線的決定**：要不要寄出、要不要 merge、能不能動正式環境、要不要花這筆錢。
- **方向選擇**：兩個方向都合理，成員無法自己判斷哪個對，需要你選一個。
- **超出原本交代範圍**：交代的事做完了，成員想多做你沒要求的事，需要你決定做不做。
- **兩份依據互相矛盾、成員自己解不開**：文件與程式對不上、兩份規格各說各話、任務描述與現況不同、先前的決定與眼前的狀況牴觸。成員會先依現有資訊自己釐清；只有解不開、而且需要你裁定時才開卡，卡上會寫清楚期望、現況與差距。

**不需要開卡的情況：**

- 單純回報進度、確認收到、通知性質的訊息，用一般聊天即可。
- 成員查得到、算得出、試得出來的事。

關卡要放在真正需要你決定、而且決定錯了要付代價的步驟上。關卡太多，你得一直盯著螢幕；關卡太少，成員可能在你想管的地方自己做了決定。

預先標好的關卡之外，成員在任何還沒做完的步驟遇到需要你決定的事，也會當場開請示卡。怎麼回覆請示卡，見 [交代工作與回覆請示卡](daily.md)。

## 手冊的傳承

成員做這類任務時學到、之後還用得到的經驗，會寫成「任務傳承」，掛在這本手冊底下。之後任何成員打開這本手冊，不論是正職還是外包，都會一起讀到這些任務傳承。

傳承記的是判斷原則，例如 SOP 漏了一個會影響結果的例外。SOP 本身該改時，成員會開卡請你核可修改，不會用傳承代替。傳承怎麼查看與管理，見 [讓成員記住你教過的事（傳承）](lore.md)。

## 一個完整例子：審查 PR

### 建立手冊

到 **設定 › 任務手冊**，按「新增類型」，顯示名稱填「審查 PR」，然後在任務定義回答三題。

**這是什麼任務？**

> 有人提供一個 PR 連結（從 Slack、控制台或任何管道），需要有人看完並給出可執行的意見。目標是作者看完就知道要改哪裡，不是只留一句 LGTM。

**需要哪些資訊？**

| 欄位 | 設定 |
| --- | --- |
| `pr_url` | 🔑 識別鍵（必填） |
| `slack_thread`：從哪一串對話進來，有就填 | 選填 |
| `focus`：這次特別想看什麼 | 選填 |

**該怎麼做？**

```markdown
1. 讀 PR：取得 diff、確認 CI 結果、確認 PR 要解決的問題。
2. 對照需求：確認 PR 解決了需求描述的問題，沒有做多或做少。
3. 從正確性、測試涵蓋、對既有行為的影響三個角度各看一遍，各自寫成一份結論檔。
4. 合併三份結論：每一條意見要有「檔案:行號、為什麼是問題、建議怎麼改」。
5. 關卡：請 owner 決定要 approve 還是 request-changes。
6. 在 PR 上留下結論；若是從某串對話進來的，把摘要貼回那串對話。

邊界：
- 不要直接修改對方的程式碼。
- 無法判斷問題是既有缺陷還是這個 PR 造成的，開卡問，不要猜。
```

最後在「負責成員」設定由誰負責。想同時審好幾個 PR，可以選外包，並設定機器與雇用數量。

### 請求進來

PR 連結可以由回呼端點從外部服務送進來（設定方式見 [讓外部事件自動送給成員（回呼端點）](webhook.md)），也可以是你在聊天裡直接貼給成員。兩種方式對任務來說是同一件事。

收到請求的成員會比對手冊，判斷這是「審查 PR」，然後先開一張請示卡請你確認任務內容。你確認後，成員才建立任務。同一個 `pr_url` 已經有一張還沒結案的任務時，成員會沿用那一張。

### 成員規劃步驟

負責的成員讀完 SOP 後，依這張任務的情況規劃：

| # | 步驟 | 完成定義 |
| --- | --- | --- |
| 1 | 取得 PR 與 CI 狀態 | diff 已取得，CI 結果已記錄（通過或失敗，失敗的是哪一項） |
| 2 | 正確性審查（並行） | 結論檔 `review-correctness.md` 已產出，每條意見含檔案:行號與建議 |
| 3 | 測試涵蓋審查（並行） | 結論檔 `review-tests.md` 已產出，列出沒有測試的路徑 |
| 4 | 影響範圍審查（並行） | 結論檔 `review-impact.md` 已產出，列出受影響的既有行為 |
| 5 | 合併三份結論 | 單一結論檔已產出，重複的已合併，互相矛盾的已標出 |
| 6 | 決定是否 request-changes（關卡） | 你已在請示卡上做出決定 |
| 7 | 在 PR 上留下結論 | PR 上有 approve 或 request-changes，結論摘要作者看得到 |

第 2、3、4 步互不依賴，可以同時進行，各自寫成自己的檔案。**同時進行的步驟後面要接一個合併步驟**（第 5 步）。系統不會檢查有沒有合併步驟，所以要把合併寫進 SOP，成員規劃時才不會漏掉。

第 6 步是關卡。計畫送出時，任務卡就會在這一步預告「等我回覆」；走到這一步時，成員開請示卡等你決定。

全部步驟做完後，任務停在「可結案」，成員請你驗收，驗收通過後再結案。
