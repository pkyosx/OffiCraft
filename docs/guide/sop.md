# 讓 AI 照 SOP 做重複的事

讀完這頁，你能把一類反覆出現的工作寫成任務手冊、指定由誰負責，並寫出成員照著就能做、你事後能驗收的 SOP 與完成定義。

## 什麼時候該建任務手冊

一次性的事直接在聊天裡交給成員。同一類請求出現第三次、你發現自己在重複交代一樣的做法時，就該建一本任務手冊。

任務手冊定義一類工作：這是什麼任務、執行前需要哪些資訊、該怎麼做，以及這類任務由誰負責。建一次之後，每一張同類任務都照它走，你不必每次重講。

成員收到需要建任務的請求時，會先列出現有的任務手冊，拿每本手冊的「這是什麼任務？」比對，判斷這件事屬於哪一類。沒有任何一本手冊符合時，成員會把它建成沒有類型的任務，任務卡上的任務類型顯示「自由代辦」，由成員自己執行。自由代辦一樣做得完，只是每次都要從頭規劃。

## 手冊與任務計畫的分工

| | 誰寫 | 內容 | 存在哪裡 |
| --- | --- | --- | --- |
| 任務手冊 | 你，或成員經你同意後修改 | 這一類工作的用途、需要的資訊、SOP、負責成員 | 設定 › 任務手冊，跨任務長期存在 |
| 任務計畫 | 負責這張任務的成員 | 這一張任務實際拆成哪些步驟、每一步的完成定義 | 任務卡上，隨這張任務結案 |

成員規劃步驟時以 SOP 為骨架，再依這張任務的實際情況調整。任務卡怎麼看、步驟與狀態的意思，請看 [追蹤任務進度](tasks.md)。

## 新增一本手冊

1. 到 **設定 › 任務手冊**，按 **新增類型**。
2. 在「顯示名稱（例：審查 PR）」輸入一個好懂的名字，按 **建立**。系統會自動產生這本手冊的內部 ID，你不需要也不能自己填。
3. 點進剛建立的手冊。手冊頁有兩塊：**負責成員** 卡，以及「任務規劃」區的 **任務定義**。
4. 點 **任務定義**，依序回答三題：「這是什麼任務？」「需要哪些資訊？」「該怎麼做？」。三題各有自己的 **編輯** 按鈕，可以分開改、分開存。
5. 回到手冊頁，在 **負責成員** 卡按 **編輯**，設定這類任務由誰負責。

新增的手冊一開始是空白的。顯示名稱可以在手冊頁的標題上直接改；留空時會顯示內部 ID。

## 這是什麼任務？

這一段寫給接案的成員看，成員用它判斷進來的請求該不該建成這一類任務。寫清楚這類任務處理什麼工作、要達成什麼結果。若容易跟其他手冊混淆，寫出彼此的適用範圍。

這段只放判斷是否屬於這一類所需的資訊。執行步驟與細節寫在「該怎麼做？」。用途寫得含糊，成員分類就容易出錯。

## 需要哪些資訊？

列出執行前一定要有的欄位。每個欄位可以設為 **必填** 或 **選填**，也可以設為 **🔑 識別鍵**。設為識別鍵的欄位一律是必填。

識別鍵用來防止同一件事開出兩張任務。規則如下：

- 只在同一個任務類型裡比對，而且只比對還沒結束的任務。舊任務已完成、終止或標記重複之後，同樣的識別鍵值再進來會開一張新任務。
- 值要完全相同才算同一件事。前後空白不計，大小寫要一樣。
- 比對到既有任務時，成員會沿用那一張任務，不會另開新的。
- 沒有設識別鍵的手冊，以及自由代辦任務，不會自動去重。

挑識別鍵的原則：選「這件事是什麼」，不要選「這次從哪裡進來」。以審查 PR 為例，身分是 PR 本身，識別鍵只放 PR 連結。如果把「從哪一串 Slack 對話進來」也設成識別鍵，同一個 PR 從另一串對話被提起，或你直接在控制台貼連結，就會被當成不同的事而開出第二張任務。

識別鍵可以由多個欄位組成，但每個欄位都必須是身分的一部分，例如「同一個 repo 的同一個版本號」。

## 該怎麼做？

這一段就是 SOP，成員規劃任務步驟時以它為藍本。寫法建議：

- 依執行順序寫步驟，每一步說清楚要產出什麼。
- 寫出邊界：哪些事不能做、什麼情況要先問你。
- 需要你決定或驗收的地方，直接寫明，成員規劃時會把那一步設成關卡。

SOP 有版本紀錄：在 SOP 的編輯模式按 **版本紀錄**，可以看舊版、比較差異、還原。用途與欄位不留版本。SOP 有字數上限，數值在 **設定 › 參數調整** 的「任務手冊 SOP 字數上限」，詳見 [設定與參數](settings.md)。

成員可以修改手冊的用途、欄位與 SOP。成員在執行中發現 SOP 本身該改時，會開請示卡把原文與修改後的內容並列，說明影響與理由，等你同意後才改。

## 設定負責成員

**負責成員** 卡決定這類任務由誰執行，只有你和特助能設定，一般成員改不了。按 **編輯** 後有兩種選擇：

- **指定成員**：從正職成員裡選一位，這類任務都由這位成員負責。
- **外包**：每張任務由伺服器雇用一位外包執行，做完就解僱。選外包時要再設定：
  - **AI 執行環境**：Claude 或 Codex。
  - **模型**：可以留空，使用預設模型。
  - **投入程度**：低、中、高、極高、最高。
  - **機器**：外包要在哪一台機器上執行。清單上會標出每台機器目前是閒置、忙碌或離線。
  - **雇用數量**：這一類任務最多同時雇用幾位外包，可以設為 **無限**。

外包一定要選機器。沒選機器、或選的那台機器離線時，這類任務的外包一律不會被喚醒，也不會改到其他機器執行，原因會顯示在該外包上。外包遲遲沒有開始時，先檢查負責成員設定裡的機器。

雇用數量是每一類任務各自的上限。另外還有全站的外包上限，在辦公室左欄「外包」分頁底部的 **招攬新成員** 設定（外包上限設定 › 最多雇用）；設為 0 時顯示「已暫停指派」，所有外包都不會被雇用。外包與正職的差別、什麼時候該用外包，請看 [增加成員與發外包](members.md)。

**解除設定** 會清掉負責成員設定。

## 內建手冊與刪除手冊

任務手冊頁分成「內建」與「自訂」兩組。OffiCraft 內建兩本手冊：「建立／修改角色」與「建立／修改任務手冊」。內建手冊可以修改，不能刪除。改壞時，在 SOP 的版本紀錄打開「預設內容」，按 **同步預設內容**，整本手冊（包含負責成員）會回到預設設定。

自訂手冊可以按 **刪除** 移除。刪除會一併移除手冊的定義、SOP 與版本紀錄，無法復原。這個類型還有未結束的任務時不能刪除，要先讓那些任務結束。

## 寫好完成定義

成員規劃的每一個步驟都必須寫完成定義（DoD），也就是「怎樣算做完」。沒寫完成定義的計畫送不出去；但完成定義寫得好不好，系統擋不了，要靠 SOP 引導、由你把關。

好的完成定義是可觀察的結果，不是要做的動作：

| 不好 | 好 |
| --- | --- |
| 跑一下測試 | 全部測試通過，且新增的三條檢查各自實測會擋 |
| 處理好 PR | PR 上留下 approve 或 request-changes 的結論 |
| 等部署完成 | 已發佈到 registry，健康檢查通過 |

判斷標準：任何人讀完這句話，都能客觀判斷它有沒有達成。一個完成定義只寫一個結果；寫了兩件事，就會出現「做完一半」這種無法判定的狀態，應該拆成兩個步驟。

你可以在 SOP 裡直接寫出每一步期望的完成定義，成員規劃時就會照著寫。

## 哪些步驟該設成關卡

關卡是成員規劃時預先標出、需要你決定或驗收的步驟。計畫送出時，任務卡就會在這些步驟上顯示「等我回覆」的預告，你一開始就知道整件事會在哪裡需要你。走到關卡時，成員會開一張請示卡，等你回覆後才繼續。

成員遵循的原則是：只有需要你本人決定、核可、提供資訊或採取行動的事才開卡；查得到的資料、自己做得到的動作，成員會自己處理。

**適合設成關卡的情境：**

- **有代價、不可逆、或碰到風險界線的決定**：要不要寄出、要不要 merge、能不能動正式環境、要不要花這筆錢。
- **方向選擇**：兩個方向都合理，成員無法自己驗收，需要你選一個。
- **超出原本交代範圍的延伸**：交代的事做完了，成員想多做你沒要求的事，需要你決定做不做。
- **兩份權威打架、成員自己解不開**：文件與程式對不上、兩份規格各說各話、任務描述與現況不同、先前的決定與眼前的狀況牴觸。成員會先依現有資訊自己釐清；只有解不開、而且需要你裁定時才開卡，卡上會寫清楚期望、現況與差距。

**不需要開卡的情境：**

- 單純回報進度、確認收到、通知性質的訊息，用一般聊天即可。
- 成員查得到、算得出、試得出來的事。

關卡要放在真正需要你決定、而且決定錯了要付代價的步驟上。關卡太多，你得一直守在螢幕前；關卡太少，成員可能在你想管的地方自己做了決定。

預先標好的關卡之外，成員在任何還沒結束的步驟遇到需要你決定的事，也會當場開請示卡。怎麼回覆請示卡，請看 [交代工作與回覆請示卡](daily.md)。

## 手冊的傳承

任務的步驟全部完成後，任務會停在「可結案」。負責的成員會開請示卡請你驗收，驗收通過後，判斷這次執行有沒有值得留下的經驗；有才寫，沒有就不寫。

在有類型的任務裡寫下的傳承，會歸在那本手冊底下，成為「任務傳承」。之後任何成員打開這本手冊時，都會一併讀到這些任務傳承，不論是正職還是外包。任務傳承的分量受「任務傳承字數上限」限制。

傳承記錄的是判斷原則與處理方式，例如 SOP 漏了一個會影響結果的例外。若是 SOP 本身該改，成員會開卡請你核可修改，而不是用傳承代替。你可以在 **傳承** 分頁篩選某本手冊的任務傳承、調整狀態，或從條目按 **開啟任務手冊** 回到手冊。傳承的完整操作請看 [讓成員記住你教過的事](lore.md)。

## 一個完整例子：審查 PR

### 建立手冊

到 **設定 › 任務手冊 › 新增類型**，顯示名稱填「審查 PR」，然後在任務定義回答三題。

**這是什麼任務？**

> 有人提供一個 PR 連結（從 Slack、控制台或任何管道），需要有人看完並給出可執行的意見。目標是作者看完就知道要改哪裡，不是只留一句 LGTM。

**需要哪些資訊？**

| 欄位 | 設定 |
| --- | --- |
| `pr_url` | 🔑 識別鍵（必填） |
| `slack_thread`：從哪一串對話進來，有就填 | 選填 |
| `focus`：這次特別想看什麼 | 選填 |

**該怎麼做？**

```markdown
1. 讀 PR：取得 diff、確認 CI 結果、確認它要解決的問題。
2. 對照需求：確認它解決了需求描述的問題，沒有做多或做少。
3. 從正確性、測試涵蓋、對既有行為的影響三個角度各看一遍，各自寫成一份結論檔。
4. 合併三份結論：每一條意見要有「檔案:行號、為什麼是問題、建議怎麼改」。
5. 關卡：請 owner 決定要 approve 還是 request-changes。
6. 在 PR 上留下結論；若是從某串對話進來的，把摘要貼回那串對話。

邊界：
- 不要直接修改對方的程式碼。
- 無法判斷問題是既有缺陷還是這個 PR 造成的，開卡問，不要猜。
```

最後在 **負責成員** 設定由誰負責。想同時審好幾個 PR，可以選外包並設定機器與雇用數量。

### 請求進來

PR 連結可以由回呼端點從外部服務送進來（設定方式請看 [讓外部事件自動送給成員](webhook.md)），也可以是你在聊天裡直接貼給成員。兩種方式對任務來說是同一件事。

收到請求的成員會比對手冊，判斷這是「審查 PR」，然後先開一張請示卡請你確認，內容包含任務名稱、要解決的問題、任務類型、驗收條件（AC）、預計的執行者與執行設定。你確認後，成員才建立任務；如果同一個 `pr_url` 已經有一張還沒結束的任務，就沿用那一張。任務會交給手冊設定的負責成員，或由伺服器雇用外包。

### 成員規劃步驟

負責的成員讀完 SOP 後，依這張任務的情況規劃：

| # | 步驟 | 完成定義 |
| --- | --- | --- |
| 1 | 取得 PR 與 CI 狀態 | diff 已取得，CI 結果已記錄（通過或失敗，失敗的是哪一項） |
| 2 | 正確性審查（並行） | 結論檔 `review-correctness.md` 已產出，每條意見含檔案:行號與建議 |
| 3 | 測試涵蓋審查（並行） | 結論檔 `review-tests.md` 已產出，列出沒有測試的路徑 |
| 4 | 影響範圍審查（並行） | 結論檔 `review-impact.md` 已產出，列出受影響的既有行為 |
| 5 | 合併三份結論 | 單一結論檔已產出，重複的已合併，互相矛盾的已標出 |
| 6 | 決定是否 request-changes（關卡） | 你已在請示卡上做出決定 |
| 7 | 在 PR 上留下結論 | PR 上有 approve 或 request-changes，結論摘要作者看得到 |

第 2、3、4 步互不依賴，可以同時進行，各自寫成自己的檔案。並行的步驟後面要接一個合併步驟（第 5 步）；系統不會檢查有沒有合併步驟，所以把這一步寫進 SOP，成員規劃時才不會漏掉。

第 6 步是關卡。計畫送出時，任務卡就會在這一步顯示「等我回覆」的預告；走到這一步時，成員開請示卡等你決定。

全部步驟完成後，任務停在「可結案」，成員請你驗收、處理傳承，再結案。
