先前寬版驗收只留了像素量測、沒留畫面,這裡把畫面補上。

## 怎麼拍的

- 起站:`cd frontend && npm run dev -- --port 5199`。前端預設走 mock adapter
  (`frontend/src/api/index.ts`,`VITE_USE_MOCK` 未設 = mock),`AuthGate` 在 mock 模式
  **不會**出現登入牆、直接進辦公室,所以不需要登入步驟。
- 驅動腳本:`shoot.mjs`(和 `canvas-sides.mjs` / `zonecheck.mjs` 同一套做法 —— 從
  `frontend/package.json` 取 playwright)。`node shoot.mjs builtin|canvas|pack`。
- 每張都停在**監控頁**:這一頁有帳號卡、機器表格、AI 會話表格,內容欄一變寬,表格就跟著
  攤開,寬窄差異一眼可見(辦公室頁中間大多是空聊天區,看不出來)。
- 數字全部是實測:外區 =(視窗寬 − `.app__main` 實際寬)/ 2,內容欄 = `.app__main` 實際寬,
  橫向捲動 = `document.scrollingElement.scrollWidth > clientWidth`。原始輸出在
  `measurements.jsonl`。

## ⚠️ 一個和任務描述不符的事實:寬版沒有外區

任務要「寬版看得出左右外區與內容欄的關係」「確認外區在不同寬度下維持固定寬度」。
**實際行為是:寬版的外區固定為 0px**,內容欄吃滿整個視窗。

這不是 bug,是 owner 2026-07-27 當天改回去的決定,程式碼裡有原註記
(`frontend/src/components/chrome.css` 第 23–33 行):

> 本票一度依 owner 2026-07-27 的「寬版左右兩邊還是要有一點外區」改成每側保留 48px,
> 同日他看過實際效果後改回 ——「寬版好像真的看不出什麼,不然寬版就不要留白好了」。
> ⇒ 最外層畫布(含主題背景圖)成為**窄版限定**的一層,寬版看不到它。

所以下面寬版三張(1440 / 1280 / 1040)的外區都是 0px —— 「外區在不同寬度下維持固定寬度」
這個檢查在寬版不成立(它固定是 0)。真正會出現外區的是**窄版且視窗寬 > 1040px**。

### 第 22 張是怎麼拍到的(以及為什麼前面說拍不到)

原生 `<select>` 的彈出層由 WindowServer 繪製、不在網頁畫面裡,所以
`page.screenshot()` 永遠拍不到它 —— 這就是第 20 張當初改用「強制攤開」的原因。
這次改走 OS 螢幕截圖,**拍到了**:

- **headed 瀏覽器**(`chromium.launch({ headless: false })`)開在固定位置,
  用 macOS 的 **`screencapture`** 抓,腳本是 `native-popup.mjs`。
- 踩到的一個坑:這個 shell 位在 launchd 的 **Background session**,直接跑
  `screencapture` 只會得到 `could not create image from display`;要用
  **`launchctl asuser <uid>`** 丟進 Aqua session 才畫得出來。
- **沒有跳出任何權限視窗** —— 螢幕錄製權限本來就已經授權過,一次就成功。
- 截的範圍是 **`-R` 指定的瀏覽器視窗那一塊**(`window.screenX/Y/outerWidth/outerHeight`
  算出來的 `40,65,1200,860`),**不是整個桌面** ——桌面上有使用者的私人內容,
  不該進到要拿給別人看的截圖裡。
- 原生彈出層是 modal 的:Playwright 的 `click()` 會一直等到它關掉才 resolve,
  所以腳本**刻意不 await** 那個 click,趁彈出層開著的當下才截。
- 附一張同視窗、同一條 screencapture 路徑但**未展開**的對照
  `native-popup-before.png`,證明 22 那張的差別真的是彈出層本身。

⚠️ 一句話總結給 owner:第 20 張是「把同一顆 select 強制攤開」的示意(DOM 真、
但不是他點下去會看到的樣子),**第 22 張才是他真正點開時長的樣子**。

### 🔴 實測結論:精靈村底下那兩個群組標題,對比度 **1.98:1**,遠低於 AA 的 4.5:1

`.ts-group-head` 的字色寫死成
`color-mix(in srgb, var(--color-marker-fg) 65%, var(--color-marker-surface))`,
兩端都是**主題包蓋不到**的槽(`--color-marker-fg: #e7e8ee`、`--color-marker-surface: #191c24`),
而這組值是**照著內建深色主題**挑的。混出來永遠是同一顆淺灰 **#9fa1a7**,不管背景是深是淺。

實測(前景取 `getComputedStyle().color`;背景取該標題方框**實際畫出來的像素**眾數 ——
所以 80% alpha 的分區底色疊在村莊背景圖上的結果也算進去了):

| 主題 | 標題 | 前景(計算色) | 背景(實際像素) | 對比度 | AA 4.5:1(11px 屬一般文字) |
| --- | --- | --- | --- | --- | --- |
| 內建深色「辦公室」 | 內建 | `#9fa1a7` | `#191c24` | **6.57:1** | ✅ 過 |
| 內建深色「辦公室」 | 自訂 | `#9fa1a7` | `#191c24` | **6.57:1** | ✅ 過 |
| 精靈村(自訂,淺色)· 1440 | 內建 | `#9fa1a7` | `#e4e3bb` | **1.98:1** | ❌ **不過** |
| 精靈村(自訂,淺色)· 1440 | 自訂 | `#9fa1a7` | `#e4e3bb` | **1.98:1** | ❌ **不過** |
| 精靈村 · 手機 375 | 內建 / 自訂 | `#9fa1a7` | `#e4e3bb` | **1.98:1** | ❌ **不過** |

1.98:1 連「非文字元素 / 大字」的 3:1 門檻都過不了。畫面上就是第 24、26 張看到的樣子:
兩個標題淡到幾乎和奶油色底融在一起,得盯著看才讀得出來。

**這是本票設計引進的問題,不是主題包的錯。** 第四輪 BLOCKER-A 為了不讓主題包把標題調成
隱形,把顏色從可覆寫的 `--color-text-muted` 改成不可覆寫的 `--color-marker-*` ——
防住了「被惡意調成隱形」,卻換來「在淺色包底下自己就接近隱形」。`theme-settings.css`
第 78–80 行的註記自己也寫了「At 11px this is normal-size text, so it must clear WCAG AA
(≥4.5:1) — it is now the ONLY thing on screen that says which kind a row is」;
**現況是淺色包底下並沒有 clear**,而且它正是唯一的歸屬標示(每列的 chip 已於 `650754c` 移除)。

修法不在本次量測範圍內,但可選項大致是:marker 槽改成隨主題明暗自動翻轉(例如
`light-dark()` 或由主題包宣告 `colorScheme` 後在 `:root[data-scheme]` 給第二組值),
或改用一個「一定壓得住背景」的算法(對比度計算後選黑/白),而不是寫死一顆灰。

### 還有誰吃 marker 色槽?只有這一條

用 CSSOM 掃過執行期所有 stylesheet 的每一條規則(含巢狀),搜 `--color-marker-`,
**全站只命中 1 條**:

```
.ts-group-head { color: color-mix(in srgb, var(--color-marker-fg) 65%, var(--color-marker-surface)) }
```

設定頁上其他元素(清單列、圖示鈕、按鈕、麵包屑)都吃一般的主題 token,精靈村自己有給值,
不受這個問題影響 —— 第 24 張裡除了那兩個群組標題以外,其餘文字都清楚可讀。

原始輸出(含每張的 `groupHeads` 陣列、背景像素眾數與佔比、CSS 層次)在 `measurements.jsonl`。
