# 提案：這個系統沒有把「時間」當成輸入

> 狀態：**提案，尚未經維護者採納。** 由使用者提出，指出一個目前在系統裡找不到落腳處的能力並提出一個最小形狀；本文不含實作承諾，落點與到期語意都待維護者裁量。

## 摘要

**缺什麼**：這個系統沒有地方可以宣告「某個時刻要做某件事」。時間到了不會有任何東西把它叫起來，做完了也沒有地方記——那件事目前唯一的存放位置是人的腦袋。

**提議做什麼**：加一組排程宣告——觸發時刻、可空的重複規則、到期要生的那件事、負責人。既有的時間迴圈掃到就建一件走既有任務通路的任務；完成之後寫回宣告，在系統外做掉的也送得回來。

**要動多少**：不新增任務的資料模型、不引入排程器函式庫、不新增投遞通道、不處理時區與行事曆語意，宣告掛在既有的設定物件上。真正新增的只有三樣：一組宣告欄位、tick 裡的一段掃描、一個外部完成入口。

## 一、提議的形狀

**一段話的概觀**：把「未來的某個時刻」變成 server 上可以宣告的東西——到期時 server 生一件既有形式的任務，做完再寫回那條宣告。先界定缺口，再談宣告的形狀（1.1）、到期的動作（1.2）、完成的寫回（1.3）與不必新增什麼（1.4）。

一個常駐 agent 的工作分成兩類。第一類由事件推起來：有人指派任務、有訊息進來、某個量測值越過門檻。這一類有完整的通路——有物件、有狀態、有負責人、有完成定義，系統會主動出手。

第二類由時間決定：「下週五做某件事」「每個月核對一次那份清單」「這份文件擱置一段時間就該回頭看」。這一類沒有任何承載的位置：不是任務、不是訊息、也不是設定，唯一存在的地方是人的腦袋。

缺口的邊界值得先講清楚：

> **這個系統已經有事件驅動的提醒，但沒有任何時間驅動的東西。**

提醒本身是有的，而且做得細——去重、抑制、只送給該收的那一個連線。缺的是觸發源：既有的提醒全部由狀態或事件推起來，沒有一條能由「時間到了」推起來，也沒有地方可以宣告一個未來的時刻。

agent 又是可丟棄的 session，長期狀態全存在 server 上，「靠 agent 自己記得」因此在結構上不成立——記得的那個 session 下一分鐘可能就不存在。**時間只能是 server 的性質，不能是 agent 的性質。**

到期時要產生的是**一件走既有任務通路的任務**，不是一則提醒訊息。既有的兩條提醒是 best-effort、at-most-once，註解自己寫明離線的 agent 就是會漏接；事件驅動的 nudge 可以接受漏接，同一件事還有別的入口，時間驅動不行——那個時刻不會再來。任務是有狀態的物件，沒被處理就一直留在那裡，這正是漏接時需要的性質。

### 1.1 一個排程宣告長什麼樣

- **觸發時刻**：一個絕對時刻，代表下一次該到期的時間點。這一格永遠有值，是排程被掃到的唯一依據；一次性宣告只有這一格，它就是全部。
- **重複規則（可空）**：空值即一次性。有值時它只回答一件事——這一次到期之後，下一個觸發時刻往後推多久。重複因此是一次性之上的附加，一次性走主幹，而不是「重複次數等於一」的分支。
- **要生出來的那件事**：到期時建立的任務的標題與完成定義。寫在宣告裡而不是到期才決定，是為了讓人看一眼宣告就知道它會叫自己做什麼。
- **負責人**：到期任務指派給誰。少了這一格，任務會生在沒有人的地方，等同沒生。
- **起算基準**：二選一——下一次從「上次完成」起算，或從「上次觸發」起算。這是斷點二（做完之後沒有回饋路徑，見第二節）的接點：選完成時間就必須拿得到完成事件，選觸發時間這條排程就退化成盲目的固定間隔。寫成明示的選擇，是要讓「沒有完成回饋」在宣告層面就看得見。
- **上次觸發時間／上次完成時間**：兩個由系統寫的時間戳，是「上一次是什麼時候做的」唯一的答案來源。
- **啟用狀態**：一次性完成後要有地方落腳，重複排程要能暫停而不必刪除。

兩個例子。**某個未來的日子要交出某份彙整**：觸發時刻是那天早上，重複規則空，做完就結束。**每個月核對一次某份清單**：重複規則是每月一次，起算基準選完成時間，下一次因此從實際核對完的那一刻往後推一個月。

### 1.2 到期那一刻，server 做什麼

1. 既有的時間迴圈每次 tick，掃出所有「觸發時刻已過且啟用中」的宣告——是「已過」不是「等於現在」，停機期間過去的到期，開機後第一輪就會被掃到。
2. 依宣告裡的標題與完成定義建一件任務，走既有的任務通路。
3. 指派給宣告上的負責人。
4. 在任務上留一個回指宣告的標記——這是之後寫回去的唯一憑據。
5. 把「上次觸發時間」寫成這一刻。
6. 有重複規則就算出下一個觸發時刻寫回宣告；沒有就把宣告移出待掃範圍。

### 1.3 完成之後怎麼寫回去

**系統內完成**：任務進終態時，順著來源標記找回宣告，寫入完成時間；若起算基準是完成時間，下一個觸發時刻在這一刻重算。

**系統外完成**：一個「這件事已經做完了」的宣告動作，由人直接落在宣告上，帶一個完成時刻（預設為現在），效果與上一條相同——寫完成時間、重算下一次、順手收掉還開著的那件到期任務。它用在事情實際上是在系統外面做掉的時候。沒有這一格，完成紀錄永遠只涵蓋恰好發生在系統內的那一部分。

**收尾**：一次性宣告完成後不刪除，改成非啟用並保留完成時間——「做過了」跟「從來沒有過這條排程」必須長得不一樣。重複排程留在啟用狀態，帶著新算出的觸發時刻。

### 1.4 這個提案不需要新增什麼

- 不新增任務的資料模型：到期產物就是既有的任務，狀態機、指派、收尾全部重用。
- 不引入排程器函式庫：時間迴圈與 tick 已經在跑，改的是把待掃對象從寫死的四條換成可讀取的宣告。
- 不新增投遞通道：任務怎麼被看見、怎麼被領走，沿用既有那一套。
- 宣告掛在既有的設定物件上，不是新的一層。
- 不處理時區與行事曆語意：重複規則只算「往後推多久」，這是刻意的縮減。

真正新增的只有三樣：一組宣告欄位、tick 裡的一段掃描、一個外部完成入口。斷點三（上游變更與後續動作之間沒有連鎖，見第二節）之後要接，是把「觸發時刻」換成「某個上游物件被修改」，其餘欄位一格都不動；但若現在把宣告寫死成只吃時間，之後就會長出第二套平行的排程機制。

## 二、為什麼需要它：三種斷點

**結論先講**：這一格不補會壞在三個獨立的地方——時間到了沒有東西把事情叫起來、做完之後沒有回饋路徑、前置變更與後續動作之間沒有連鎖。

範疇也容易被縮小：**缺的不是「週期性」這個特例，而是排程性整體。**「每兩週做一次」跟「下週五做某件事」缺的是同一個東西，而後者更常見——多數該記得的事只發生一次。把問題寫成「週期性工作沒有落腳處」，解法就會長成一個只吃間隔的機制，一次性排程反而接不上去。

三者獨立，但會互相退化。

### 斷點一：時間到了，沒有任何東西會把事情叫起來

該做的事退化成「靠人記得」：人記得它就發生，人忘記它就無限期不發生，而且不發生不會產生任何訊號。實務上它常要等到撞上某個邊界才被想起，而那個時機跟「什麼時候該做了」無關。

**週期性至少還有下一次，一次性排程連那個退路都沒有。** 漏掉一次「每兩週」，下一次還會再來，人有機會自我修正；「下週五做某件事」錯過就是永久錯過——沒有失敗、沒有告警、沒有紀錄，那個時刻只是安靜地過去了。

### 斷點二：做完之後沒有回饋路徑

這一節不能只講「完成狀態沒有欄位」，因為最自然的解法會讓它更糟。

用外部 calendar 當觸發源是合理的：重複規則、提醒、時區、跨裝置，這些早就被 calendar 解掉，不值得重造。但那樣一來，**「做完了」會被勾在 calendar 上，也就是勾在系統邊界之外**。**外部觸發源解決了「叫起來」，卻把「做完了」推得離系統更遠。**

具體會怎麼壞：

- 下一次到期無法從「上次完成」起算，只能用固定間隔盲目地叫，叫了也不知道有沒有被處理，很快成為噪音。
- 「已經做過了」跟「從來沒做過」長得一模一樣，任何盤點與狀態總覽都不可信。
- 出現兩份真相：一份在 calendar 上（人勾的），一份在系統裡（殘缺的），沒有對帳的方法。人要知道現況只能自己去系統外面看一眼，而那一眼本身又是一件沒有觸發的排程工作——斷點會自我複製。

所以真正要補的不是觸發器，是**一個「宣告完成」的入口**：能從系統外面明確送進來，不是只在任務被系統關閉時才更新。就算最後真的接外部 calendar，這一格還是得自己做。

### 斷點三：前置變更與後續動作之間沒有連鎖

有一類工作不由時間到期，而由上游改變而到期，但上游變更與下游動作之間沒有邊。失敗的形狀是漂移累積：上游改了好幾次，下游一次都沒跟上，等到有人想起來要修，成本已從小修變成重做。（這是一般性的漂移模式，我沒有對這個系統做過實測觀察。）它需要的不是時間，是「變更能產生任務」的能力；沒有連鎖時人只能靠「定期回頭檢查一次」來補，於是退化成前兩條。

## 三、這不是從零長一個新東西

**結論先講**：需要的零件多半已在 runtime 裡跑——時間迴圈、tick、提醒通路都有，缺的只是可宣告的觸發源。

**一、沒有任何排程器。** 全 repo（含 go.mod）掃 `cron|crontab|robfig|gocron|quartz`，零命中。

**二、但 runtime 已經在跑定時工作。** 四條形狀一致的 goroutine 掛在 server 啟動路徑上（reconcile、outsource、auto-update、backup），都是 `go func(){ for { time.Sleep(x); tick() } }()`，而 `sleep-then-tick` 這個詞就寫在這些函式自己的註解裡。時間迴圈與 tick 的能力都已經存在；缺的是把它從寫死的四條變成可宣告、可設定的一等公民。

**三、提醒機制存在，但觸發源全是事件。** 兩條 directed band 的註解逐字用了 reminder：一條在 agent 的 context 量測越過門檻時 `pushes a directed "start converging" WARN reminder`；另一條在任務進入終態時提醒走完收尾，`The reminder walks the WHOLE ... close-out`。兩條都是狀態／事件驅動、不可宣告、不由時間到期——提醒的通路是通的，時間這個輸入不存在。

backup 那條 cadence 的註解裡還有一句，本身就是這個提案的論證：**「a backup that has to be armed is a backup nobody has.」** 同樣的句型可以直接套上來——**需要人記得的排程，就是沒有排程。**

## 四、想先問清楚的問題

**結論先講**：形狀我有把握，落點我沒有——四題決定宣告掛在哪一層、到期行為怎麼定。

1. **這件事在不在既有規劃裡？** 如果已有規劃中的排程機制涵蓋它，這提案應該併進去。
2. **排程定義該掛在哪一層？** 角色、任務手冊、還是獨立物件？這決定它能不能跨角色共用，我沒有背景判斷你們的偏好。
3. **錯過的到期怎麼處理？** server 停機期間過去的一次性到期，補發還是丟棄？重複排程到期時上一件還沒完成，累積還是跳過？
4. **到期任務沒被處理，該不該有第二次訊號？** 若要有，得先決定它跟既有 nudge 的去重規則怎麼共存。

## 五、這個提案的弱點與可能被拒絕的理由

**結論先講**：最有力的反對是第 1 條「用外部 calendar 就好」，最可能讓提案整個消失的是第 2 條。

1. **「用外部 calendar 就好」在這個範疇下更有力，我必須正面承認。** 一次性排程、時區、重複規則、跨裝置提醒，calendar 全都成熟解決了。我的立場不是反對，而是：**外部 calendar 能解掉斷點一，解不掉斷點二**——勾掉的動作發生在系統外。合理的結論可能是「觸發源用外部的，完成回饋自己做」，重心因此從 1.2 移到 1.3——而 1.3 的兩條寫回路徑本來就不預設是誰觸發的。

2. **「宣告完成」的入口可能跟既有的任務關閉語意重疊。** 若既有的關閉流程加一個欄位就覆蓋大半，這個提案的一半就消失了。我沒把握它在你們的資料模型裡是不是這麼便宜。

3. **時間驅動的提醒最容易退化成被忽略的噪音，我沒有完整解法。** 一個被叫起來做「請檢查某某」的 session，敷衍做完與認真做完的產出長得一樣。部分解法是讓到期任務帶上具體標的，但這需要每一類工作自己提供候選。

4. **這是一個容易變大的提案。** 寫下來很小，真做起來會長出時區、失敗重試、到期堆積、離線行為。如果判斷終點是一整套排程子系統，拒絕是合理的；折衷是只收下 1.1–1.3 這個最小形狀。

5. **成效無法正向度量。** 這類工作防的是「該做而沒做」造成的緩慢劣化，漏掉不會產生錯誤訊息，「因為沒做而出事」的次數統計上永遠接近零。這跟備份同類，不構成不該做的理由，但它沒辦法用數據自證，排優先序時一定吃虧。

6. **斷點三依賴一個我沒查證的前提**：系統對上游物件是否有統一的變更事件可以掛。若沒有，斷點三的成本遠高於時間驅動的那部分，應切開單獨評估。

7. **三種斷點也可能不該綁在一起。** 它們共用同一個問題陳述，解法成本卻差很多；寫在一起有助於說明形狀，卻讓提案難以部分接受。

8. **一次性與重複硬塞同一個資料形狀，會先從重複那一側裂開。** 「觸發時刻永遠有值、重複規則只負責往後推多久」對一次性很乾淨，但重複一旦要表達「每月最後一個工作天」或「每週二與週四」，往後推多久就不夠用，勢必長成一套規則語言，屆時「同一個形狀」只在簡單情況成立。我選擇先只支援固定間隔，這是可以被合理反對的取捨。

9. **「起算基準」這一格可能根本不該存在。** 讓每條排程自己選從完成或從觸發起算，等於把一個語意分歧丟給宣告的作者，同一份清單上的兩條排程行為會不一樣。合理的反對是：只該有一種語意。我保留它是因為第 1 條——外部觸發源的情況真的拿不到完成事件——但這是妥協，不是設計。

10. **系統外完成的入口是一個沒有防護的寫入點。** 它直接改動完成紀錄與下一次到期，卻沒有任何東西能確認那件事真的做完了。斷點二的整個論證建立在「系統裡的紀錄比 calendar 上的勾更可信」，而這一格把可信度還原成「填的人說了算」。
