## 核心名詞

### 成員（Member）
工作室裡的 AI 成員。分**正職（Staff）**與**外包（Outsource）**兩種，兩者共用同一套 presence 與
同一個詳情面板外殼（`AgentDetailPanel`），欄位差異寫在 §1.4 / §1.5。

| 欄位 | 說明 |
|---|---|
| 名字 | 顯示名稱（例：Mira）。外包沒有名字，用**代號（codename）**，畫面上一律寫成「外包 · 代號」|
| 成員 id | 這個成員的穩定 id，就是各處用來定址他的那一串（例：`mira`、`m-3417933c8632`、`ow-7eed74b85026`）|
| 角色 | 擔任的角色（正職才有；外包沒有角色）|
| 狀態 | 離線 / 喚醒中 / 線上 / 停止中 / 已停止（`office.presence` 五個值）|
| AI 執行環境 | Claude Code 或 Codex —— **agent 回報過的值**，沒回報過是 `—` |
| 模型 | **agent 最近一次開機回報**的模型，沒回報過是 `—`（不是設定值）|
| 思考強度（Effort）| 低 / 中 / 高 / 最高（`mp.effortOf`）|

### 成員狀態機
presence 是 **server 端算出來的**，不是 agent 自報的心跳狀態。核心錨點只有兩個變數：
1. **online = 由 SSE 連線判定**（`online == connected`）——server 依 agent 是否「正持著 `ocagent listen` 的 SSE 連線」直接判定：持著＝online、SSE 一斷＝offline。**沒有 agent 要自己維持的 heartbeat**（舊設計的 heartbeat 已移除）。**warden 亦同一套**——warden 自己連上 SSE ＝ online（2026-07-10 起 member 與 warden 一視同仁；權威 spec 見 [state-model.md](state-model.md)）。
2. **喚醒中（waking）** 由一個時間錨點決定，而**第一個寫它的是 server，不是 agent**：reconcile 把 START 派給 warden、warden 接走的那一刻就 stamp（`stampWakeObservability`），而按下喚醒時 server 會在**同一次請求裡**就重決一次（`reconcileMemberNow`），所以接得走的話錨點當場就蓋上了，不必等下一個 tick。**這樣才分得出「叫過但沒起來」與「根本沒人叫過」**——只有 agent 自報時，兩者在畫面上長得一模一樣。
   - **正職成員**的錨點是 `waking_since`；agent 開機起手呼叫 `report_waking()` 時會再蓋一次，但那時它已經是 waking 了。
   - **外包 worker 不帶 `waking_since`**（`workerReportWaking` 明寫這個欄位不在 worker 的詞彙裡）：它的喚醒中是用**這次 spawn 派出的時間**當錨點推導的（`workerPresence`），沒派出過就退回用該 row 的**建立時間**（剛建立、還在等放置的 worker 本來就該顯示喚醒中）。⚠️ 那個 spawn 時間是**純記憶體**的：server 重啟後就沒了，於是一個早就建立的 worker 會改用建立時間當錨、一算就超窗而讀成離線——**除非它其實還連著（那就是線上，或有下線意圖時是停止中）：錨點雖然照算，但推導在前面那幾步就回答完了，根本不會拿它出來問。**
   - 兩者共用同一個過期窗：錨點放著沒等到連線，一個固定窗（`WakingTTLSecs`，秒數以碼上常數為準）後推導回離線。但**在輪到這個窗之前，有三件事先被問**，照碼上的順序是：① **row 已 released 就整個不畫**（外包獨有，短路在推導核心之前）→ ② **有下線意圖就顯示停止**（兩邊皆然，SSE 還在則是停止中；錨的欄位不同：正職 `stopping_since`、外包 `desired_state`）→ ③ **還連著就是線上**（兩邊皆然）→ 才輪到喚醒窗。⚠️ 注意 ② 在 ③ 之前：連著、但已被標為要下線的，是停止中，不是線上。反過來，正職多一道外包沒有的閘：要 `desired_state` 仍是 online 才算喚醒中。⚠️ 「逾時受理由」是**另一條路**寫的（reconcile 下一次 tick 才寫，且錨的是它自己的 `LastCommandAt`），所以會出現「從沒 stamp 過 `waking_since`、卻留下逾時受理由」的組合。
   （舊設計的 `ocagent presence --phase waking` 子命令已不存在。）

其餘態由 server 從這兩個錨點 ＋ graceful-shutdown 訊號**衍生**（單一衍生核心 `deriveLiveness()`；正職走 `PresenceState`、外包走 `workerPresence`，兩個映射都收斂到同一個核心）：
```
離線(offline) ──(你按喚醒：寫下意圖 desired_state=online；面板先樂觀翻成喚醒中)──►
   ──(server 同一次請求內重決、START 被 warden 接走：蓋上錨點)──► 喚醒中(waking)
   ──(`WakingTTLSecs` 內沒連上 SSE)──► 回到 離線(offline)
   ──(agent 掛上 ocagent listen、server 見 SSE 連上)──► 線上(online == connected)
   ──(收 stopping 訊號、SSE 仍在)──► stopping ──(SSE 斷)──► stopped/offline
```
- **離線 / stopped**：灰點
- **喚醒中（waking）**：黃點 ＋ `喚醒中` 徽章（**錨點已被蓋上**——正職是 `waking_since`、外包是這次 spawn 的時間或（未曾派出時）row 的建立時間——而 SSE 尚未連上）
- **線上（online）**：綠點（server 見 agent 正持著 SSE 連線——純看連線，非 heartbeat）
- **stopping**：winding-down 內部衍生態（graceful-shutdown 訊號已設、SSE 未斷），由 server 算出，agent 不用管。

> **單一 presence 信號、單一畫點處。** 成員的狀態點由 **PresenceBadge / LifecycleDot** 這一個 presence 信號源畫；**Avatar 本身不畫點**（頭像只是頭像），避免兩處各畫一顆點而彼此不同步。

> **個人頭像優先序（2026-07-27 owner 裁定）。** owner 可在正職／外包詳情替指定 stable member id 上傳、替換或移除個人圖片；一般成員不可管理。所有主要身分露出一致採「個人圖片 → 角色／主題圖片 → 內建 glyph」，圖片載入失敗也沿同一鏈回退。個人圖片不影響 presence，亦不以可變的 display name 當 key。契約、儲存與 rollback 見 [per-member custom avatar](member-custom-avatar.md)。

### 停止階梯（下線 → 加速 → 強制）
正職與外包共用同一顆按鈕元件（`MemberActionButtons`）與同一組字（`lifecycle.action`）：
`喚醒` / `取消` / `停止` / `加速停止` / `強制停止`。

- presence 決定前綴鍵：離線 `[喚醒]`、喚醒中 `[取消, 喚醒]`、線上 `[]`、停止中 `[喚醒]`、已停止 `[喚醒]`。
- 線上／停止中時**多一格階梯鍵**，這一格現在踩在哪一階由 `stopLadderStageOf` 決定：`停止 → 加速停止 → 強制停止`。
- 剛升級的那一階會被 disable 一小段時間（`LADDER_ARM_MS`），免得連按兩下替你再升一級；
  disable 的理由是有字的（`lifecycle.reason.alreadyStopping` / `.justAppeared`）。
- **沒有線上機器時喚醒鍵是 disabled**，理由 `machine.noOnlineMachine`「沒有線上的機器」。
- **強制停止有確認對話框**，內文明寫「現在就砍掉 session、跳過正常收尾。進行中的未存工作會遺失。」

⚠️ **這個階梯與「換 model／換機器」的關係，寫在 [docs/guide/members.md](../guide/members.md)**：
一個線上、手上還有沒收完狀態的成員，改設定會先開一個收尾窗，**不送 kill／start、沒有時鐘**
（但會朝它扇出一則收尾預告），直到它自己回報停止或 owner 按**加速停止**——那一刻才 kill＋重生，
新值跟著下一手起來。**強制停止不在這條路上**：它把 `desired_state` 壓成 `offline`、清掉 refocus
epoch 再當場砍，**沒有重生**，所以存下的新值要等之後某一次**重啟／喚醒**才生效
（`HandleForceStopMemberApiMembersMemberIdForceStopPost` / `HandleForceStopOutsourceWorkerApiOutsourceWorkersIdForceStopPost`）。
碼上是**兩個對稱的決策點**，不是一個：正職走
`memberHasStateToFlush` / `armMemberOwnerOpHandover`（`server/ocserverd/member_ownerop_winddown.go`），
外包走 `respawnWorkerForOwnerOp` / `openOwnerOpHandover`（`server/ocserverd/worker_spawn.go`）；
兩者共用述詞 `hasUncollectedOnlineOwnerOpState`，但**不共用外殼**（該檔逐格寫明哪幾格不一致、以及為什麼不准壓平）。

### 全域情境（Global Context）
**目標**是送到 agent 眼前的每一句話都住在一份 owner 編輯得動的文件裡：開機時讀的、以及被收走／被轉派／被指派任務時收到的那一則。於「設定 › 全域情境」檢視，依 owner 的讀法分組（**上線／下線／任務事件**三組）。（T-a241 之前它們住在「設定 › 角色誌」裡面的一個區塊；owner 2026-08-25：「這些 global context 已經脫離角色太遠了 應該有自己的獨立頁面」。）

✅ **十份全部接上了送出端** —— 編輯這些文件，改變的就是 agent 實際收到的字。（上一版這裡寫著「只有一部分接上，其餘編輯了也不會改變 agent 收到的字」。那句在接線補完之後就過期了，而**這種過期比一個過期的名字危險**：它會勸退一個其實可以編輯的動作，而且沒有任何測試會因為它變假而變紅。）

🔴 **這裡刻意不列「有哪幾份」。** 那種清單一定會過期，而且不會有任何東西紅 —— 這一段本身就曾經寫著「三塊」而當時已經是四份。要知道有哪幾份，看 `spec/openapi.json` 的 `BootDocKind` enum：它是 `kind` 的合法值，服務端的 registry 與它對質，座艙的列表以它為索引。（以前這裡指向 `list_boot_docs`；owner 2026-08-23 裁掉了那支端點 —— 它不會過期，但它也不會讓任何東西失敗，而 enum 會。）

讀寫走一組泛型端點 `/api/boot-docs/{kind}/{key}`（**動詞是 POST，打 PUT 會拿到 405**）；三個較早的具名端點仍在，服務同一批文件。**讀取與寫入的形狀刻意不對稱**（owner 2026-08-23）：讀回來有 `text`（整份）、`read_only_head`、`body`；寫入**只收 `body`**。授權下限：讀＝機器層，寫與還原出廠＝owner 或 admin 特助，**逐份相同**。

⚠️ **這一段以前接著寫「有兩份是唯讀的，任何人的寫入都回 405」，以及「唯讀區由伺服器接回去」—— 兩句今天都不成立**（T-6f44 的決定 2 把最後兩份開放編輯；而系統互動、兩份啟動步驟、〈停止〉這四份**根本沒有唯讀區**，整份就是本體）。兩條機制都還在、也都還走得到：`read_only` 由 server 回答，有唯讀區的那幾份寫入時伺服器仍會把它接回去。**但今天沒有任何一份出貨文件是唯讀的，也不是每一份都有唯讀區** —— 所以這裡描述的是機制，不是清單。要知道哪一份現在長什麼樣，看 `bin/tests/fixtures/boot-doc-registry.tsv`（`read_only` 與 `has_head` 兩欄，server／座艙／conformance 三側都釘在它上面）。

## 1. 辦公室（Office）

預設首頁。版面：左＝成員側欄（固定 264px）、右＝對話區；窄螢幕（`office--mobile`）時兩者互斥、
只顯示其一，對話區頂端多一顆「返回成員」。

`OfficePage` 其實會渲染**三選一**（由 hash 路由決定，不是同時存在）：
- `#office/worker/<id>` → **只有**外包詳情面板（整頁，無側欄無對話區）
- `#office/member/<id>` → **只有**正職詳情面板（整頁）
- 其餘 → 上面那個兩欄版面

### 1.1 頂部列
- **左**：公司標誌 ＋ 組織名稱 ＋ 鉛筆編輯（Enter／失焦儲存）。標誌只是品牌顯示，此區**無點擊行為**（不會開啟聊天）。
- **右**：重新整理、設定齒輪、個人檔案下拉。版本號**不在頂列**，在 設定 › 系統更新與備份。

### 1.2 成員側欄
側欄頂部是**兩個分頁**（`OfficeSidebarTabs`，`role="tablist"`；分頁狀態是本地的，不進 hash）：

| 分頁 | 標題 | 副標 | 未讀 |
|---|---|---|---|
| **正職（Staff）** | `office.staffTitle`「正職」| `${n} 人` | 紅色未讀數，>99 顯示 `99+` |
| **外包（Outsource）** | `office.outsource.title`「外包」| `${n} 人` ＋ ` · 上限 {cap}`（`-1` 顯示 `∞`；未設上限時整段省略）| 同上 |

**正職列（`MemberCard`）** —— 整列可點（點進聊天），列上：
頭像鍵（`stopPropagation`，點進**成員詳情**）、名字、`PresenceBadge`（狀態點 ＋ 角色）、未讀數徽章。
⚠️ **沒有離線文字徽章、頭像上沒有狀態點、列上沒有齒輪。**

**外包列（`OutsourcePanel`）** —— 整列可點（點進聊天），列上三行：
① 頭像鍵（點進**外包詳情**）＋「外包 · 代號」；② 狀態點 ＋ 任務編號 chip（點進 `#tasks/<id>`）
＋ 任務類型（沒有類型時是 `tasks.adhoc`「自由代辦」）；③ **當前任務標題**，沒有進行中任務時
顯示「無當前任務」。`maxParallel === 0` 時列表上方掛一句「已暫停指派」。

**側欄最下方：招攬新成員**（`office-recruit`）—— 依當前分頁分流：
- 在 **正職** → 直接路由到 `#settings/roles/new`（設定 › 角色誌 › 新增角色）
- 在 **外包** → 就地打開**外包上限設定** popover（`最多雇用` 步進器 0–20、`無限` 切換、`完成`）

### 1.3 對話區（聊天）
`ChatArea`。頭列：頭像、名字、`PresenceBadge` 或自訂副標、當前任務標題（有才畫）、
「查看這位成員未完成的任務」鍵（正職才有）、「開啟這個角色的定義設定」鍵（有角色才有）、
「檔案與圖片」圖庫切換。整條頭列在可點時就是進詳情面板的入口。

- 訊息區：依日分組（今天／昨天／`M月D日 (週X)`）、已讀標記、未讀分隔線、
  底部浮動物（**二選一，永不同時出現**）：最新那一則不在視野內時的**回到最新箭頭**，
  以及有未見新訊息時**取代它**的**新訊息預覽列**（寄件者＋一行內容，點擊落在最新那一則）、
  「已到最早訊息」、逐則「回覆這則」與引用條、成員間對話預設收合（「N 則成員間對話 · 展開」）。
- **附加檔案／圖片**（拖放或迴紋針，支援直接貼上圖片）。
- **空狀態**：`chat.emptyRange`「這個範圍還沒有訊息」。
- **離線但可留言**時另有一張離線卡與一顆就地**喚醒**鍵。
- **輸入框會被鎖住**的兩種對象：已釋出的外包、已不在名單的成員 —— 那時只顯示一行
  「{name} 目前離線中」，沒有輸入框。

### 1.4 正職詳情面板
`MemberDetailPanel` = 共用外殼 `AgentDetailPanel` ＋ 五個插槽。外殼由上而下固定渲染：
**返回 → 身分卡 → overlays → afterIdentityCards → 資訊卡 → afterInfoCards → 運行狀況卡
→ 最近操作卡 → 終端卡 → extraExpandCards → 初始 PROMPT 卡 → afterPromptCards。**

**身分卡** —— 頭像（owner 可上傳／替換／移除）、名字（內嵌改名）、**成員 id 徽章**、
`PresenceBadge`；動作列＝線上時多一顆**更改**，其後是停止階梯（見「停止階梯」那一節）。
下方掛喚醒／換機器的**未派出告警**（`DispatchAlert`）。

**資訊卡** —— 左欄：`AI 執行環境`、`模型`（附「最近一次開機回報」提示）、`EFFORT · 思考強度`；
右欄：`機器`、帳號。四格都可能掛一個待生效提示（`→ 要換成` / 機器是 `→ 要換到`）。

**運行狀況卡** —— 🧠 `context`（Codex 另附 `壓縮：N`）＋ **重新聚焦** 鍵（僅線上可按）；
💲 `估計$`；以及收尾中／上次重新聚焦的註記。

**最近操作卡** —— 動詞（喚醒／停止）、結果（成功／失敗）、時間、理由、可展開的「查看記錄」。

**終端 · TMUX 卡** —— `$ tmux …` 指令 ＋ 複製鍵，說明「在你自己的終端機貼上執行，即可接上這個成員的 session。」

**初始 PROMPT（可展開）** —— 依這個**角色**的目前開機內容即時重組的預覽。

**正職獨有的兩張卡**（`extraExpandCards`）：
- **回呼端點 · WEBHOOK** —— 端點 ID（建立後不可改）、用途、平台（通用／Slack／GitHub，
  後兩者必須填簽章密鑰）、複製 URL、啟用／停用、輪替密鑰、刪除；以及**事件統計** modal
  （最後收到、丟棄數與原因、最近請求可展開看 headers／body）。
- **定期訊息 · SCHEDULE** —— 與外包共用同一個元件。

**`afterPromptCards`**：`RESUME SUMMARY` 卡（喚醒快照的度量與內容預覽）。

**更改／喚醒對話框**（同一個 `mp-settings-dialog`，線上時標題是「更改」、離線時是「喚醒」）：
`ModelEffortEditor`（執行環境／模型／思考強度）＋ **機器下拉**（離線機器 disabled），
底下三顆：`取消`、**`只儲存，不喚醒`（僅離線時出現）**、確認。
註記逐字：「這裡設定的是『下次喚醒要用哪一個』。」

### 1.5 外包詳情面板
`WorkerDetailPanel`，**同一個外殼**，所以返回／資訊卡／運行狀況／最近操作／終端／初始 PROMPT
六張卡與正職**是同一份 code**。差在四個插槽：

| 插槽 | 正職 | 外包 |
|---|---|---|
| `afterIdentityCards` | 無 | **委託任務** 卡（任務編號 · 標題 ＋ 狀態 chip，可點進任務） |
| `afterInfoCards` | 無 | **委託人** 卡 |
| `extraExpandCards` | 回呼端點 ＋ 定期訊息 | **只有定期訊息**（外包沒有 webhook） |
| `overlays` | 強制停止確認 ＋ 更改對話框 | 更改對話框 |

其餘差異：身分卡的名字是「外包 · 代號」；沒有 session 時動作列只有一顆**喚醒**（打開同一個更改對話框）；
`上次換手`（正職是「上次重新聚焦」）；初始 PROMPT 多一句說明它是**依目前開機說明即時重組**、
內容是正職那份扣掉整個 persona，且**不含任務與手冊**。

**已釋出（released）的外包**是唯讀歷史：只剩返回鍵、一張身分卡（「外包 · 已釋出」／
「此外包成員已結案釋出,這裡是唯讀的歷史紀錄」）與委託任務卡；**沒有**資訊／運行狀況／最近操作／
終端／PROMPT 卡，也沒有任何生命週期按鈕。

### 1.6 重新聚焦（Refocus）
壓縮／整理成員的 context。只有**線上**時可按，位於 context% 旁；離線時的提示是「僅線上可重新聚焦」。

## 2. 請示（Ask）

`RepliesPage`，單欄，兩個區塊（**沒有**頁內標題列、**沒有**篩選列）：

### 2.1 待回覆
標題 `請示 · N`。空狀態：「✓ 目前沒有待處理的請示」。依開卡時間**新到舊**排序。

每張卡：
- **卡頭**：發問者頭像（點進其詳情面板）、名字＋角色（外包顯示「外包 · 代號」、不顯示角色）、
  **跳到原訊息**、**標為過期**。
- **兩個時間戳**：`開卡 <絕對時間>`、`已等你 <時長>`（每 30 秒跳一次）。
- **任務參照列**（卡片綁著任務時才有）：任務標題 ＋ **查看任務詳情**（跳 `#tasks/<id>`）。
- 摘要與內文（Markdown）、提問附件。
- **選項 chip**：一個選項一顆，帶 `ai_pick` 的那顆（多選卡可能不只一顆）帶「AI 建議」標——**看標記，不看位置**。
  「AI 建議」**只由那個標表達，chip 本身不上色**（owner 2026-08-31：「AI建議的都不要特別標顏色好了，
  右邊已經有label了，現在的顏色就只用在使用者選的時候」）——重點色現在只有一個意思：**你選的那顆**。
- **選項左緣**：**多選卡是打勾框**，單選卡是**序號 1/2/3/4**（owner 2026-08-31：「單選可以跟之前一樣
  顯示 1, 2, 3, 4 就好嘛？」）。打勾框只長在多選卡上，因為只有多選卡有「已勾、還沒送」這個看得見的狀態
  要表達——它同時是「這顆被勾了」的**形狀**訊號（不只靠顏色）與「這是多選卡」的表達。單選卡點一下就送，
  沒有那個狀態，圓鈕在那裡是純裝飾。無障礙語意照這條走：多選 chip 是 `role="checkbox"` ＋
  `aria-checked`；**單選 chip 就是一般 `<button>`**（沒有持續的選中狀態可以宣告，`role="radio"` 是一個
  守不住的承諾）；已回覆／已過期卡上的選項是唯讀的靜態回顧，不帶角色也不可按。
- **按下去會發生什麼，分兩種**（owner 2026-08-31 裁定，卡 `rc-06bc715358c2`：「單選卡點一下就送出，
  多選卡才要按送出」）：
  - **單選卡**：點一下那顆選項**就是回答**，當場送出。輸入框裡已經打的字**跟著同一次送出**，不會被丟掉。
  - **多選卡**：點下去是**勾選**、不是回答（想勾幾顆都行，會顯示「已選 N 項」），勾好的選項與下面打的字
    由**同一顆送出鍵**一次送出。多選卡**一打開就已經幫你勾好帶 `ai_pick` 的那幾顆**（owner 2026-08-31：
    「多選的時候，UI 應該要預設就先把我勾好 AI 建議的」）；沒有 `ai_pick` 的多選卡開起來是空的。
    **單選卡永遠不預先勾**——它點一下就送，預先勾等於預先送。
  - 兩種卡都一樣：**整份空白（沒圈、沒打字）的答覆送不出去**（多選卡把預設的勾全部取消掉之後也一樣送不出）。
- **自由輸入**：`輸入回覆…`，可帶附件。

**標為過期**要走一次確認，內文逐字說明它**不算回答**：成員會收到通知，問題還在的話他會重新開卡。

### 2.2 近期已處理
一顆可展開的區塊鍵「近期已處理 · N」，**預設收合、收合時根本不去抓資料**；副標
「已回覆或已標為過期的事項 · 已回覆的可重新決定」。只列**最近 24 小時**內處理掉的；一張都沒有時
整個區塊不渲染（沒有空狀態）。

- **已回覆**卡：「你選的」標（圈到的**任何一顆**帶 `ai_pick` 時另帶「AI 建議」）＋ 答案；多選卡
  圈了幾顆，答案就是那幾顆並列。可展開「查看當初選項」，圈到的那幾顆標「目前」；再按 **重新決定**
  就能改選或改寫。
- **已過期**卡：「已過期」標 ＋ 說明「未被回答、已標為過期;若問題還在,成員會重新開卡」；
  選項只能看不能點，沒有輸入框。

### 2.3 篩選列與深連結

**篩選列**：一個 ID 篩選欄位 ＋ 「清除篩選」（只在篩選中時出現）。比對是**不分大小寫的子字串**，所以貼一整個 id 是完全命中、只打一半也還在收斂。它是一個**普通篩選**（owner 2026-09-05, `rc-2085e5ec60be`：「我預期功能都一樣／只是連過去幫忙帶篩選參數而已」）——沒有「找不到」提示；除了下面那條一次性的已處理載入之外，自己不打任何 API。

`#replies/card/<cardId>`：**把那個 id 代入 ID 篩選**，另外把命中的那張卡捲進畫面並 focus
（`RepliesPage` 的 scroll effect，沿用自通知點擊那條路）。它不是一套獨立的定位機制——
沒有它篩選一樣成立，捲動只是讓命中在已處理區時不必自己往下找。
⚠️ 中間那一節 `card/` 是必要的（`hashRoute.ts` 要求 `rest[0] === "card"`）；少了它會被解析成 `#replies`，**靜默失效**。
⚠️ 空狀態有兩句，跟任務頁同一個分法：沒有篩選時是「✓ 目前沒有待處理的請示」，篩不到時是「沒有符合篩選條件的請示」。兩句不可合併——後者若說成前者，會在六張卡等著時告訴 owner 他已經回完了。
⚠️ 待回覆那一段篩不到、且已處理那一段還沒載入時，會自動展開並載入它一次（否則收合中的卡會被篩成「沒有符合」——一個假的空）。
**這件事一次 visit 只做一次**（`handledAutoloadTried`）：`loadHandled` 是兩支沒有 in-flight 去重的請求，而載入旗標要等它們回來才翻，沒有這道閂就會變成每敲一個字元發兩支。
**而且待回覆還在載入時不得觸發**：那時 `waiting` 是空陣列，意思是「還不知道」，不是「沒有命中」。
⚠️ 標題的「· N」只有在已處理**已載入**時才改用篩過的長度；未載入時仍用 server 的整段計數。
🔴 這一格是有牙齒的：那個 0 一旦代表「還沒撈」，下面的 zero-hide 會把整段連同展開的把手一起刪掉。篩選中時該段**一律不隱藏**，即使數字是 0 —— 否則「沒有符合」與「這一段不存在」在畫面上長得一樣。
🔴 **射程（這一格容易被寫寬）**：待回覆那一段（`waitingReplyCards`）**沒有時間窗**，所有未回覆的卡都在，多久以前開的都篩得到；24 小時的窗只切**已回覆**與**已過期**兩段（`replyCardAnsweredWindowSecs`）。⇒ 篩不到的，只有**已回覆或已過期且超過 24 小時**的卡。**這是 owner 具名接受的代價**（2026-09-05, `c-0e183a7fbb10`：「已回覆已經標示24 hrs才有資料，所以真的列不出來也沒關係」），不是缺口——不要為它偷加一支 by-id 讀取。

## 3. 任務（Task）

`TasksPage`，單欄：篩選列 → 空狀態 → `未結束` 區 → `已結束` 區。

### 3.1 篩選列
三顆多選下拉 ＋ 一顆 **清除篩選**。

| 篩選 | 全選時的字 | 選項 |
|---|---|---|
| **負責人** | 所有負責人 | `外包`、`未指派`，以及每一位正職；**每個選項帶筆數**，筆數 0 的選項除非已勾選否則隱藏 |
| **類型** | 所有類型 | 每一種任務類型（手冊 displayName，退回 key）＋ `自由代辦` |
| **狀態** | 所有狀態 | 尚未執行／進行中／等我回覆／等待外部／轉派中／已完成／終止／重複 |

- **狀態是 server 端篩選**（推給 hook）；負責人與類型是前端判斷。
- **預設**：狀態勾好五個非終局值（尚未執行、進行中、等我回覆、等待外部、轉派中），
  負責人與類型都空。因此**清除篩選鍵一開始就看得到**——按下去會把終局狀態也一起放進來。
- `轉派中` 不是狀態而是鎖：任務 `lock === "reassigning"` 且未終局時也會被這一格撈到。

### 3.2 兩個區塊
- **未結束 · N** —— 依優先權（高 → 中 → 低 → 凍結）再依建立時間新到舊。
- **已結束 · N** —— 可展開，**預設收合**；依結案時間新到舊。終局＝已完成／終止／重複。
  有 `#tasks/<id>` 錨點時自動展開。

**兩個空狀態**：完全沒有任務時是「目前沒有任務」；有任務但篩掉光了是「沒有符合篩選條件的任務」。

### 3.3 任務卡（`TaskCard`）
整張卡可點開合（預設收合）。**收合時就看得到**的東西：

- **徽章列**：任務編號（點一下複製）、**優先權**（未結案時是下拉：高／中／低／凍結）、
  **狀態**（下拉選單：查看等我回覆卡／查看等待外部節點／標記重複／終止；結案後後兩項 disabled）、
  `轉派中` 鎖徽章、**任務類型**（帶齒輪，點進該類型的設定）、**產物**（有才畫，開 popover）。
- **標題**（唯讀）。
- **四個「人」的欄位**：`負責人`（＋傳訊息、＋**轉派…**）、`建立者`（與負責人相同時整列隱藏）、
  `前任`（被轉派過才有）、`識別鍵`（是網址就變可點連結）。
- **依賴列**：`等 <taskNo>` ＋ 依賴任務的狀態與標題，可點進去。
- **進度列**：進度條 ＋ `步驟 N/M · 已歷時 <時長>`（結案後凍住）。
- **訊息輸入框**（未指派時 disabled）。

**展開後**才畫：任務敘述（Markdown，空的話是「尚未填寫敘述」）、以及**工作流程**時間軸——
一步一列，帶步驟名、`審批` 標、耗時、狀態徽章、DoD、備註（可開全螢幕閱讀）、等待外部的理由，
以及**內嵌的請示卡**（步驟綁著回覆卡時）。並行步驟包在「同時進行 · N 項並行」的區塊裡。

⚠️ 還沒有步驟時分四種說法，各自不同：載入失敗／載入中／`等待指派`（未指派）／
`等待 <負責人> 建立 Steps`。

### 3.4 深連結
- `#tasks/<id>` —— 覆蓋全部三個篩選，只顯示那一張（並自動展開已結束區）。
  **找不到時錨點留著**，畫面答「沒有符合篩選條件的任務」，出口是「清除篩選」（它連同 hash 一起還原）。
  舊行為是靜默把 hash 復原回 `#tasks`，owner 2026-09-05（`rc-428906235337`）裁定改掉：一條指向不存在的連結
  與一條根本沒在篩選的連結在畫面上長得一模一樣。
  ⚠️ **「找不到」與「載不到」是兩句話**：只有 `GET /api/tasks/{id}` 回 404 才算找不到；其他失敗（500、離線）
  走 `anchorFailed`，畫面顯示載入錯誤而不是空狀態 —— 對一個沒能問出口的問題不得給答案。
- `#tasks/executor/<memberId>` —— 一次性種子：把負責人篩選設成那一位、清掉類型、狀態回預設，
  然後把 hash 正規化回 `#tasks`。

## 4. 監控（Monitor）

`MonitorPage`，一頁三區塊（即時遙測資訊）。

### 4.1 帳號資訊（Accounts）
每帳號一張卡；空狀態「尚無帳號用量資料」。
- 狀態點、**帳號名**（可就地改名）、`· 機器名`、右側 **估計 $花費**、**帳號詳情** modal
  （歸戶 key、帳號識別碼、組織 UUID、Email、組織、**回報標籤原文**、使用機器）
- **5 小時窗**：`· 用量 X% · 時間 Y%` ＋ 進度條（填色＝用量、標記線＝時間進度）
- **7 天窗**：同上；用量燒太快標 **`· 過熱`**
- 每個用量數字旁標 **`量於 X 前`**；沒有戳記時誠實留白。

> 比較「用量 %」與「時間流逝 %」，燒太快就示警（Claude 訂閱用量窗口）。
> ⚠️ **過熱只在「還在回報」的帳號上判定**：用量百分比是上次回報的快照、時間百分比卻是即時算的，
> 拿沒人更新的數字去比還在走的時鐘，紅點會變成時間的函數。沒有人回報時就不判定（數字照留）。

### 4.2 機器資訊（Machines）
表格，一列一台機器。**欄位（`monitor.machineCol`）**：
**機器** ｜ **Claude** ｜ **Codex** ｜ 🖥 CPU ｜ 🎚 RAM ｜ 🔌 電源 ｜ **操作**

⚠️ **上一版這裡寫的是「機器 ｜ 帳號 ｜ CPU ｜ RAM ｜ 電量 ｜ 電源」**，那是 M1 的欄位：
帳號那一欄早就拆成 Claude／Codex 兩欄，而且多了一整欄**操作**。

- 機器名可就地改名；列上帶線上／離線。
- **操作**欄的三件事：**安裝／重新安裝 warden**、**拆除（uninstall）**、**刪除機器**，
  各自有自己的確認與結果 modal（拆除是 danger 兩段確認）。
- 表格下方是 **`+ 新增機器 / 上線`** 入口（填機器名 → 建立）。空狀態：「尚無機器,請先新增機器 / 上線」。

### 4.3 AI 會話（AI Sessions）
表格，一列一個運行中的成員 session（**點列 → 開該成員／該外包的詳情面板**；外包列帶 Outsource 小標）：
**成員**（頭像＋名字＋狀態點＋`角色 · 狀態`）｜ **機器** ｜ **帳號** ｜ **模型**（＋effort 徽章）｜ 🧠 context ｜ 💲 估計$

> **effort 徽章＝真實即時 reasoning-effort（非 owner-intent）。** Sessions 這欄的 effort 是 agent **當下**的 reasoning-effort，走既有 token-usage telemetry 便車、跟 model / cost 同源同路：
> **statusLine（`effort.level`，反映 session 中途 `/effort` 變更）→ `_build_telemetry`（agent 端組包）→ `POST /api/monitoring/telemetry` → `MonitoringSessionDTO.effort` → FE `session.effort`**。honest-empty：尚未上報時是 `""`，UI 顯示破折號「—」，不假造。
> 對照：成員詳情面板（§1.4 資訊卡）的 effort 是 **`member.effort`（owner-intent）**——那是「想要多少」的意圖值、不是即時值。兩者刻意分流：Sessions 看真實即時、詳情面板看意圖。

### 6.1 系統更新與備份
麵包屑 `設定 › 系統更新與備份`。
- **目前版本**、MCP 目錄雜湊等 build 身分資訊
- 若已最新：「✓ 已經是最新版」；若有新版：「有可用的新版本」＋ **升級到最新版**
- **接收 Beta 版本**（更新檢查納入 GitHub prerelease）
- **自動更新**（偵測到新版本就在背景升級並重啟）·**預設關閉**
- 備份健康
- **簽章金鑰**（T-62）— 目前有幾把、各自何時產生、哪一把在簽；「產生新金鑰」（不登出任何人、不必重啟）與「移除」（撤銷，無復原，連同該金鑰簽過的分享連結一起失效；確認框必須講出這個代價與「warden 憑證不會自己過期」）。T-80 起，機器換金鑰這件事會自己收斂（伺服器觀察每台用的是哪一把、看到舊的就請它自己去換），移除的判準因此從「都重新連過了嗎」變成可數的「每一台都已經換到新金鑰了嗎」；**這個數字目前只在機器清單的 API 資料裡（`token_key_id` / `token_key_current`），還沒有做進畫面。**
- 不重複顯示組織名稱

### 6.2 全域情境
麵包屑 `設定 › 全域情境`。整塊就是事件程序文件（T-a241 之前它是「角色誌」裡面的區塊 1）。

- 依 owner 的讀法分組（**上線（BOOT）／下線（STOP）／任務事件（TASK）**三組），每份一列，
  **不顯示 .md 檔名**。**份數與分組不寫在這裡**：`spec/openapi.json` 的 `BootDocKind` enum 是答案，
  而前端的列表是一張以它為索引的 `Record<BootDocKind, …>`，少一列編譯不過。
- 一般一列 = 一份文件：點進 → `BootDocPage`：檢視 markdown；**編輯** → 編輯模式，模式內有版本歷史，
  **還原出廠版在版本清單的「初始版本」那一列**（不是頁面上的並列按鈕；出廠 seed 不被覆蓋，永遠拿得回來）。
- **每一份的唯讀區都畫在編輯框上方**，看得到、改不動，編輯中也不收起來（owner 要對著它寫下半）。
  它不是唯讀文件的專利，也不是一個灰掉的輸入框：wire 上根本沒有欄位可以送它。
- **整份唯讀的那條路**：一樣點得進去、看得到全文，但沒有編輯器、沒有還原、沒有版本紀錄，
  改為一句說明它是什麼。`read_only` 由 server 回答，前端不硬編是哪幾份。
  ⚠️ **今天沒有任何一份出貨文件走這條路** —— 所以這一段描述的是機制、不是現況。
- **一種 kind 服務多份時**（今天只有〈啟動步驟〉：Claude／Codex 各一份，第三步互相矛盾所以不能合併），
  那一列點進去是**索引頁**（`boot`），再點一列才進 `BootDocPage`（`bootRuntime`）。
- **使用者自訂**是例外，它走較早的另一套機制：點進 → 詳情頁；**重置**＝清空
  （回到未撰寫的 `預設` 空塊；boot context 組裝時空塊整塊跳過）。

### 6.3 角色誌
麵包屑 `設定 › 角色誌`。**只有角色相關的東西**（事件程序文件已於 T-a241 搬到 §6.2）。

- **列表**：角色卡片，每張顯示 頭像、**角色標題**、描述。列表最下方有**新增角色定義**
  （＝多請一位正職；`#settings/roles/new` 就落在這裡），每一列也帶刪除。
- **詳情頁**三份文件，各自有自己的字數上限：
  - **角色定義（Duty）** —— 檔名 ＋ 檢視 markdown；**編輯** → 編輯模式
    （**取消編輯／重置／完成編輯**，重置＝還原預設角色定義）
  - **判準（Insight）** —— 跟學習經驗**分開的一份**，由該角色的成員自己搬進來。
    ⚠️ **不是私有的，只是分開的**：任何已認證成員都讀得到；**寫**才有限制
    （只有該角色自己的 agent 與 admin）。
  - **學習經驗（Lessons）** —— 這個角色累積下來的教訓，**同一角色的每個 session 共享**。
    ⚠️ **回寫是執行成員自己的收尾義務，不是系統自動做的**（server 只推一則提醒；
    唯一的寫入面是 `replace_lessons` / `patch_lessons`）。責任歸屬的權威說法在
    [docs/guide/tasks.md](../guide/tasks.md)。

### 6.4 任務手冊
麵包屑 `設定 › 任務手冊`。每一種任務類型一本手冊：用途、需要哪些資訊、SOP、學習經驗、指派給誰。
`#settings/manuals/<key>` 深連結會直接開在那一本上（任務卡的類型徽章就是這樣跳過來的）。
手冊的 SOP 與學習經驗各有自己的字數上限（見 §6.5）。

### 6.5 參數調整
麵包屑 `設定 › 參數調整`。owner 可調的 server 旋鈕，依畫面順序：

| 參數 | key |
|---|---|
| 登入有效期 | `sessionTtl` |
| Agent token 有效期 | `agentTokenTtl` |
| Claude 第一次通知 / Claude 最後通牒 | `notice` / `handover` |
| Codex 第一次通知 / Codex 最後通牒回合 | `codexNotice` / `codexHandover` |
| 加速停止秒數 | `acceleratedGrace` |
| 監控刷新間隔 | `monitoringRefresh` |
| **五個文件字數上限** | `docCapCharsDuty` / `Insight` / `Learning` / `ManualSop` / `ManualLearnings` |
| 喚醒聊天字數預算 | `chatBudget` |
| 備份保留份數 | `backupRetain` |

⚠️ **五個字數上限是五個獨立的格子**（`DOC_CAP_ORDER`），不是一個共用值；
喚醒聊天字數預算與備份保留份數刻意**不在**那張表裡（單位與上下限都不同，各走各的 commit）。
每個參數的意義與範圍見 [docs/guide/settings.md](../guide/settings.md)。

### 6.6 主題
麵包屑 `設定 › 主題`。主題**管理**（新增／編輯／匯入／匯出／刪除）在這裡；
主題**選擇**在頭像下拉的偏好設定（owner IA：偏好＝選擇、設定＝管理）。
一套主題管得到：**顏色**（含不透明度與跟隨）、**用詞**（可覆蓋介面字，連英文標籤也能換）、
**字型**（安全白名單，內文／標題各一）、**頭像**（正職／外包／CEO／助理各一張）、
**工作室 Logo**、**導覽圖示**（五個頁籤各一張）、**外框背景圖**（平鋪／貼邊／滿版）。
玩法見 [docs/guide/theme.md](../guide/theme.md)。
