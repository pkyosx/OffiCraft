## 核心名詞

### 成員（Member）
工作室裡的 AI 成員。分**正職（Staff）**與**外包（Outsource）**兩種，兩者共用同一套 presence 與
同一個詳情面板外殼（`AgentDetailPanel`），欄位差異寫在 §1.4 / §1.5。

| 欄位 | 說明 |
|---|---|
| 名字 | 顯示名稱（例：Mira）。外包沒有名字，用**代號（codename）**，畫面上寫成「外包 · 代號」；例外是側欄外包分頁的列（分頁已寫「外包」）與卡片上的人名 chip（任務卡負責人／建立者／前任、請示卡開卡人、傳承撰寫人）只寫代號|
| 成員 id | 這個成員的穩定 id，就是各處用來定址他的那一串（例：`mira`、`m-3417933c8632`、`ow-7eed74b85026`）|
| 角色 | 擔任的角色（正職才有；外包沒有角色）|
| 狀態 | 離線 / 喚醒中 / 線上 / 停止中 / 已停止（`office.presence` 五個值）|
| AI 執行環境 | Claude Code 或 Codex —— **agent 回報過的值**，沒回報過是 `—` |
| 模型 | **agent 最近一次開機回報**的模型，沒回報過是 `—`（不是設定值）|
| 思考強度（Effort）| 低 / 中 / 高 / 極高 / 最高（`mp.effortOf`）|

### 成員狀態機
presence 是 **server 端算出來的**，不是 agent 自報的心跳狀態。核心錨點只有兩個變數：
1. **online = 由 SSE 連線判定**（`online == connected`）——server 依 agent 是否「正持著 `ocagent listen` 的 SSE 連線」直接判定：持著＝online、SSE 一斷＝offline。**沒有 agent 要自己維持的 heartbeat**（舊設計的 heartbeat 已移除）。**warden 亦同一套**——warden 自己連上 SSE ＝ online（2026-07-10 起 member 與 warden 一視同仁；權威 spec 見 [state-model.md](state-model.md)）。
2. **喚醒中（waking）** 由一個時間錨點決定，而**第一個寫它的是 server，不是 agent**：reconcile 把 START 派給 warden、warden 接走的那一刻就 stamp（`stampWakeObservability`），而按下喚醒時 server 會在**同一次請求裡**就重決一次（`reconcileMemberNow`），所以接得走的話錨點當場就蓋上了，不必等下一個 tick。**這樣才分得出「叫過但沒起來」與「根本沒人叫過」**——只有 agent 自報時，兩者在畫面上長得一模一樣。
   - **正職成員**的錨點是 `waking_since`；agent 開機起手呼叫 `report_waking()` 時會再蓋一次，但那時它已經是 waking 了。
   - **外包 worker 不帶 `waking_since`**（`workerReportWaking` 明寫這個欄位不在 worker 的詞彙裡）：它的喚醒中是用**這次 spawn 派出的時間**當錨點推導的（`workerPresence`），沒派出過就退回用該 row 的**建立時間**（剛建立、還在等放置的 worker 本來就該顯示喚醒中）。⚠️ 那個 spawn 時間是**純記憶體**的：server 重啟後就沒了，於是一個早就建立的 worker 會改用建立時間當錨、一算就超窗而讀成離線——**除非它其實還連著（那就是線上，或有下線意圖時是停止中）：錨點雖然照算，但推導在前面那幾步就回答完了，根本不會拿它出來問。**
   - 兩者共用同一個過期窗：錨點放著沒等到連線，一個固定窗（`WakingTTLSecs`，秒數以碼上常數為準）後推導回離線。但**在輪到這個窗之前，有三件事先被問**，照碼上的順序是：① **row 已 released 就整個不畫**（外包獨有，短路在推導核心之前）→ ② **有下線意圖就顯示停止**（兩邊皆然，SSE 還在則是停止中；錨的欄位不同：正職 `stopping_since`、外包 `desired_state`）→ ③ **還連著就是線上**（兩邊皆然）→ 才輪到喚醒窗。⚠️ 注意 ② 在 ③ 之前：連著、但已被標為要下線的，是停止中，不是線上。反過來，正職多一道外包沒有的閘：要 `desired_state` 仍是 online 才算喚醒中。⚠️ 「逾時受理由」是**另一條路**寫的（reconcile 下一次 tick 才寫，且錨的是它自己的 `LastCommandAt`），所以會出現「從沒 stamp 過 `waking_since`、卻留下逾時受理由」的組合。
   （舊設計的 `ocagent presence --phase waking` 子命令已不存在。）

其餘態由 server 從這兩個錨點 ＋ graceful-shutdown 訊號**衍生**（單一衍生核心 `derivePresence()`；正職走 `PresenceState`、外包走 `workerPresence`，兩個映射都收斂到同一個核心）：
```
離線(offline) ──(你按喚醒：寫下意圖 desired_state=online；面板先樂觀翻成喚醒中)──►
   ──(server 同一次請求內重決、START 被 warden 接走：蓋上錨點)──► 喚醒中(waking)
   ──(`WakingTTLSecs` 內沒連上 SSE)──► 回到 離線(offline)
   ──(成員的連線程序〔claude 是通知模組的子程序〕接上、server 見 SSE 連上)──► 線上(online == connected)
   ──(收 stopping 訊號、SSE 仍在)──► stopping ──(SSE 斷)──► stopped/offline
```
- **離線 / stopped**：灰點
- **喚醒中（waking）**：黃點 ＋ `喚醒中` 徽章（**錨點已被蓋上**——正職是 `waking_since`、外包是這次 spawn 的時間或（未曾派出時）row 的建立時間——而 SSE 尚未連上）
- **線上（online）**：綠點（server 見 agent 正持著 SSE 連線——純看連線，非 heartbeat）
- **stopping**：winding-down 內部衍生態（graceful-shutdown 訊號已設、SSE 未斷），由 server 算出，agent 不用管。

> **單一 presence 信號、單一畫點處。** 成員的狀態點由 **LifecycleDot** 這一個 presence 信號源畫，每個畫面只畫一顆。左欄清單列、聊天室 header 與詳情面板身分卡（正職與外包）把它畫在**頭像右下角**（`PresenceAvatar`，Slack 式；owner rc-734cffef6221、c-3d68c2b097e7），名字前面是運作狀態圖示（工作中是閃動的星芒、等待中是每 3 秒翻轉一次的沙漏、閒置是冒著熱氣的咖啡杯，後兩者比星芒慢且幅度小，減少動態設定下三者都靜止；可點的圖示平時只有字形，hover 或鍵盤 focus 才出現框；停止中（換手中，session 仍在跑、仍在回報）與喚醒中（server 只送開機中這個 session 自己的回報，不送比它舊的憑證的回報；同一秒發的憑證分不出來）照實際回報畫，與線上相同；離線、已停止時三處都改畫一個灰色、不動的月亮，hover 或點一下只顯示與圓點相同的狀態字，不是按鈕、不開彈窗、不能 Tab 到；喚醒中、線上或停止中但還沒回報（`activity` 為 null）時三處都畫一個灰色、不動的未知圖示（圓圈內一個問號），hover 或點一下只顯示「狀態未知」，其餘行為與月亮相同；所以左欄每一列都有圖示，整欄圖示與名字對齊；hover 看一句話說明；左欄清單與聊天室 header 的圖示點一下開「運行狀況」彈窗，詳情身分卡的點一下釘住那句說明）；監控頁仍畫在行內（PresenceBadge）。`Avatar` 元件本身不畫點。

> **個人頭像優先序（2026-07-27 owner 裁定）。** owner 可在正職／外包詳情替指定 stable member id 上傳、替換或移除個人圖片；一般成員不可管理。所有主要身分露出一致採「個人圖片 → 角色／主題圖片 → 內建 glyph」，圖片載入失敗也沿同一鏈回退。個人圖片不影響 presence，亦不以可變的 display name 當 key。契約、儲存與 rollback 見 [per-member custom avatar](member-custom-avatar.md)。

### 停止階梯（下線 → 加速 → 強制）
正職與外包共用同一顆按鈕元件（`MemberActionButtons`）與同一組字（`lifecycle.action`）：
`喚醒` / `停止` / `加速停止` / `強制停止`。

- presence 決定前綴鍵：離線 `[喚醒]`、喚醒中 `[]`、線上 `[]`、停止中 `[]`、已停止 `[喚醒]`。喚醒中不給喚醒（owner `rc-8b3d3a366c54`：喚醒中兩邊都是更改＋停止）；停止中也不給（owner `rc-2e1c96250169`：等它停完再喚醒），聊天室的 ⚡喚醒同。
- 喚醒中／線上／停止中時**多一格階梯鍵**，這一格現在踩在哪一階由 `stopLadderStageOf` 決定：`停止 → 加速停止 → 強制停止`。
- 剛升級的那一階會被 disable 一小段時間（`LADDER_ARM_MS`），免得連按兩下替你再升一級；
  disable 的理由是有字的（`lifecycle.reason.alreadyStopping` / `.justAppeared`）。
- **沒有線上機器時喚醒鍵是 disabled**，理由 `machine.noOnlineMachine`「沒有線上的機器」。
- **強制停止有確認對話框**，內文明寫「跳過正常收尾，進行中未存的工作會遺失。」

⚠️ **這個階梯與「換 model／換機器」的關係，寫在 [docs/guide/members.md](../guide/members.md)**：
一個線上、手上還有沒收完狀態的成員，改設定會先開一個收尾窗，**不送 kill／start、沒有時鐘**
（但會朝它扇出一則收尾預告），直到它自己回報停止或 owner 按**加速停止**——之後才停掉舊的一手，讀到離線才起新的一手，
新值跟著新的一手起來。**強制停止不在這條路上**：它把 `desired_state` 壓成 `offline`、清掉 refocus
epoch 再當場砍，**沒有重生**，所以存下的新值要等之後某一次**喚醒**才生效
（`HandleForceStopMemberApiMembersMemberIdForceStopPost` → `forceStopMember`，正職外包同一個函式）。
碼上是**兩個對稱的決策點**，不是一個：正職走
`memberHasStateToFlush` / `armMemberOwnerOpHandover`（`server/ocserverd/member_ownerop_winddown.go`），
外包走 `respawnWorkerForOwnerOp` / `openOwnerOpHandover`（`server/ocserverd/worker_spawn.go`）；
兩者共用述詞 `ownerOpEpochUncollected`（「已收口」讀 `stopLatchCollectsRowEpoch`：上一代留下的 `stopped_since` 只算上一代的換手），但**不共用外殼**（該檔逐格寫明哪幾格不一致、以及為什麼不准壓平）。

### 全域情境（Global Context）
**目標**是送到 agent 眼前的每一句話都住在一份 owner 編輯得動的文件裡：開機時讀的、以及被收走／被轉派／被指派任務時收到的那一則。於「設定 › 全域情境」檢視，依 owner 的讀法分組（**上線／下線／任務事件**三組）。（T-a241 之前它們住在「設定 › 角色誌」裡面的一個區塊；owner 2026-08-25：「這些 global context 已經脫離角色太遠了 應該有自己的獨立頁面」。）

✅ **十份全部接上了送出端** —— 編輯這些文件，改變的就是 agent 實際收到的字。（上一版這裡寫著「只有一部分接上，其餘編輯了也不會改變 agent 收到的字」。那句在接線補完之後就過期了，而**這種過期比一個過期的名字危險**：它會勸退一個其實可以編輯的動作，而且沒有任何測試會因為它變假而變紅。）

🔴 **這裡刻意不列「有哪幾份」。** 那種清單一定會過期，而且不會有任何東西紅 —— 這一段本身就曾經寫著「三塊」而當時已經是四份。要知道有哪幾份，看 `spec/openapi.json` 的 `BootDocKind` enum：它是 `kind` 的合法值，服務端的 registry 與它對質，座艙的列表以它為索引。（以前這裡指向 `list_boot_docs`；owner 2026-08-23 裁掉了那支端點 —— 它不會過期，但它也不會讓任何東西失敗，而 enum 會。）

讀寫走一組泛型端點 `/api/boot-docs/{kind}/{key}`（**動詞是 POST，打 PUT 會拿到 405**）；三個較早的具名端點仍在，服務同一批文件。**讀取與寫入的形狀刻意不對稱**（owner 2026-08-23）：讀回來有 `text`（整份）、`read_only_head`、`body`；寫入**只收 `body`**。授權下限：讀＝機器層，寫與還原出廠＝owner 或 admin 特助，**逐份相同**；另外開發者模式關著時，寫入、還原出廠與版本還原對任何人都回 409（使用者自訂不在此列）。

⚠️ **這一段以前接著寫「有兩份是唯讀的，任何人的寫入都回 405」，以及「唯讀區由伺服器接回去」—— 兩句今天都不成立**（T-6f44 的決定 2 把最後兩份開放編輯；而系統互動、兩份啟動步驟、〈停止〉這四份**根本沒有唯讀區**，整份就是本體）。兩條機制都還在、也都還走得到：`read_only` 由 server 回答，有唯讀區的那幾份寫入時伺服器仍會把它接回去。**也不是每一份都有唯讀區** —— 所以這裡描述的是機制，不是清單。要知道哪一份現在長什麼樣，看 `bin/tests/fixtures/boot-doc-registry.tsv`（`read_only` 與 `has_head` 兩欄，server／座艙／conformance 三側都釘在它上面）。

全部由同一個 `BootDocPage` 呈現，共用同一套編輯與版本歷史；**同步預設內容不是頁面上的並列按鈕**，它在編輯模式裡的版本清單「預設內容」那一列（owner 2026-08-14 裁定）。出廠 seed 永遠不被覆蓋，還原拿得回原文。UI 一律**不顯示 .md 檔名**（那些是內容、不是檔案）。可編輯的 .md 文件（全域情境、角色定義）一律共用同一套編輯模式：**編輯 → 取消編輯／重置／完成編輯**（重置＝還原預設）。機制細節（唯讀區與本體怎麼切、變數怎麼跑、寫入面擋什麼）見 [事件程序文件](boot-documents.md)。

## 1. 辦公室（Office）

預設首頁。版面：左＝成員側欄（固定 264px）、右＝對話區；窄螢幕（`office--mobile`）時兩者互斥、
只顯示其一，對話區頂端多一顆「返回成員」。

`OfficePage` 其實會渲染**三選一**（由 hash 路由決定，不是同時存在）：
- `#office/worker/<id>` → **只有**外包詳情面板（整頁，無側欄無對話區）
- `#office/member/<id>` → **只有**正職詳情面板（整頁）
- 其餘 → 上面那個兩欄版面

### 1.1 頂部列
- **左**：公司標誌 ＋ 組織名稱 ＋ 鉛筆編輯（Enter／失焦儲存）。標誌只是品牌顯示，此區**無點擊行為**（不會開啟聊天）。
- **右**：重新整理、設定齒輪、個人檔案下拉。版本號**不在頂列**，在 設定 › 系統更新與備份。

### 1.2 成員側欄
側欄頂部是**兩個分頁**（`OfficeSidebarTabs`，`role="tablist"`；分頁狀態是本地的，不進 hash）：

| 分頁 | 標題 | 副標 | 未讀 |

### 2.2 已回覆與已過期
選了「近期已回覆」才去抓這兩份清單；只列**最近 24 小時**內處理掉的。

- **已回覆**卡：「你選的」標（圈到的**任何一顆**帶 `ai_pick` 時另帶「AI 建議」）＋ 答案；多選卡
  圈了幾顆，答案就是那幾顆並列。答案引用了問題的一段時，答案下方顯示「引用原文」。可展開「查看當初選項」，
  圈到的那幾顆標「目前」；再按 **重新決定** 就能改選或改寫，原本的引用預設帶著（按 x 拿掉）。
- **已過期**卡：「已過期」標 ＋ 說明「未被回答、已標為過期;若問題還在,成員會重新開卡」；
  選項只能看不能點，沒有輸入框。

### 2.3 篩選與深連結

**篩選**：「顯示方式」左邊一顆漏斗鈕，右上角徽章是有值的欄位數。點下去開「篩選請示卡」：電腦是從漏斗下方展開、右緣對齊漏斗的下拉面板（外觀同「顯示方式」面板，寬 440px、不變暗背景、沒有 ✕），手機（≤720px）是從下方升起的面板、右上「完成」。欄位標籤在上、兩欄排列，編號欄佔整列：**請示卡編號**、**開卡人**、**任務優先序**、**任務到期**。它們作用在目前選中的標籤上，標籤旁的張數也跟著篩。改動**立即套用**到背後的清單，沒有套用鈕；電腦上點面板外、Esc、再點一次漏斗都會關閉（面板裡的下拉開著時 Esc 先關下拉），手機上「完成」或點暗處關閉，焦點回到漏斗。底部是「已套用 N 個條件」與「清除篩選」；「清除篩選」只在有條件生效時出現，按下去清空這四個欄位，不動選中的標籤。每次進頁面面板都是關著的。編號欄**按 Enter 或失焦才生效，不是每次按鍵**；清空欄位再按 Enter 也是清除。

套用編號時，查到的那張卡會自動選中它所屬的標籤（等待回覆／稍後再看／近期已回覆），所以不論狀態都看得到；那個標籤的張數是 1，其他是 0。之後自己切到別的標籤，清單就是篩選後的空狀態。

編號查詢向 server 要那一個 id，並把「找不到／沒問到／被其他條件擋掉」分成不同的話，語意以 `frontend/.claude/rules/chat-and-reply-cards.md` 為準。

`#replies/card/<cardId>`：**把那個 id 代入編號篩選**（因此選中那張卡所屬的標籤），另外把命中的那張卡打開、捲進畫面並 focus
（`RepliesPage` 的 scroll effect，沿用自通知點擊那條路）。它不是一套獨立的定位機制——
沒有它篩選一樣成立。
`#replies/opener/<memberId>`：聊天室標頭的請示卡跳轉。選中**等待回覆**、開卡人種成那一位、其他欄位與編號清空，所以畫面上的卡就是標頭徽章數的那幾張；hash 不正規化，重新整理照樣生效。「清除篩選」回到 `#replies`。
⚠️ 中間那一節 `card/` 是必要的（`hashRoute.ts` 要求 `rest[0] === "card"`）；少了它會被解析成 `#replies`，**靜默失效**。
⚠️ 篩選欄位有值時，任何標籤的空清單都說「沒有符合篩選條件的請示」，不說該標籤自己的空狀態——等待回覆若在六張卡被篩掉時說「✓ 目前沒有待處理的請示」，就是告訴 owner 他已經回完了。
🔴 **射程（這一格容易被寫寬）**：等待回覆與稍後再看（`waitingReplyCards`）**沒有時間窗**，所有還沒回的卡都在，多久以前開的都篩得到；24 小時的窗只切**已回覆**與**已過期**（`replyCardRecentWindowSecs`）。⇒ 篩不到的，只有**已回覆或已過期且超過 24 小時**的卡。**這是 owner 具名接受的代價**（2026-09-05, `c-0e183a7fbb10`：「已回覆已經標示24 hrs才有資料，所以真的列不出來也沒關係」），不是缺口——不要為它偷加一支 by-id 讀取。

## 3. 任務（Task）

`TasksPage`，單欄：篩選漏斗＋「顯示方式」那一列 → 空狀態 → `未結束` 區 → `已結束` 區。那一列的左端是目前篩選列出的任務數（「5 個任務」，只有一個數字，不是「顯示 x／y」）；分組時是每一組的張數加總，收合的組也算；伺服器還沒回答目前的篩選時不顯示。

### 3.1 篩選
「顯示方式」左邊一顆漏斗鈕，右上角徽章是生效中的條件數；⚠️ 預設狀態集本身就是一個篩選，所以預設徽章就是 1。點下去開「篩選任務」，形狀與行為跟請示頁相同（§2.3：電腦從漏斗下方展開的下拉面板、手機底部面板加「完成」、改動立即套用、底部「已套用 N 個條件」與「清除篩選」）。欄位是 **任務編號** ＋ 四顆多選下拉（負責人、類型、狀態、到期）。「清除篩選」只在真的有東西被篩住時才出現，在任務頁它因此預設就在。下拉**選了就生效**，編號欄位**按 Enter 或失焦才生效**。

| 篩選 | 都沒勾時的字 | 選項 |
|---|---|---|
| **任務編號** | （空欄；標題寫在欄位上方，框內不再寫一次） | 自由輸入；**精準比對**（T-93 第三輪起改為向 server 查那一個 id，不再是子字串），跟請示卡頁同一種 |
| **負責人** | 所有負責人 | `外包`、`未指派`，以及每一位正職；**每個選項帶筆數**，筆數 0 的選項除非已勾選否則隱藏 |
| **類型** | 所有類型 | 每一種任務類型（手冊 displayName，退回 key）＋ `自由代辦` |
| **狀態** | 所有狀態 | 尚未執行／進行中／等我回覆／等待外部／轉派中／已完成／終止／重複 |
| **到期** | 所有到期 | 已逾期／快到期（只列符合的未結案任務） |

- **每一軸都是 server 端篩選**：清單（`GET /api/tasks`）與計數（`GET /api/tasks/count`）帶同一組參數，負責人選項的筆數、lane 與其數量、排序都由 server 算；**任務編號以 `?ids=` 跟其他軸一起問**。清單每次拿 50 張，捲到接近底部再拿下一頁 50 張；換篩選或分組依據就從第一頁重問。
- 🔴 **打字的編號欄位與 `#tasks/<id>` 錨點是兩條路，不要合併**（T-93 第二輪，owner 2026-09-06 `rc-44347fc49338`：「任務沒有出現同樣的filter」）：
  - **錨點**種下編號並**清空其他軸（含狀態集合）**，所以指向已完成任務的連結也跳得到；
  - **欄位**打字時**一個請求都不發**（獨立審查在請示卡頁把「一個字元一個請求」列為必須改）；**按 Enter 或失焦提交後才發一支**（`?ids=`，T-118 起提交時機是 Enter／失焦）。
  - 後果照實寫出來：**打一個在目前狀態集合之外的編號會篩不到**，要先把狀態那一軸放寬。這跟其他下拉的行為一致——它們也只收斂畫面上的東西。
- **欄位寬度取自它要裝的東西，不是寫死的像素**（owner 2026-09-06「請示卡的ID好像都是固定長度？」，2026-09-07 `rc-b2beb7b1fd3c`「ID寬度要合理」）：欄位裡一份看不見的 sizer 帶著編號字數當 `min-width`；在篩選面板裡欄位填滿那一格。
  - 🔴 **框內沒有 placeholder**：標題就寫在欄位上方，框內再寫一次是重複（owner 2026-11-28「類似 ID 的 filter，已經有 title，為什麼裡面要再寫一次，都拿掉」）。任務、請示卡、傳承分區與傳承目錄四個編號欄都一樣；讀名仍是同一個標題（`aria-label`）。
  - 請示卡：編號恆為 15 字元（`api_replycards.go:283` 鑄 `"rc-" + 12 hex`，沒有例外）。
  - 任務：編號是 `T-` 加流水號（`dal_task_id_seq.go`；改制前鑄的 `t-` + 12 hex **沒有被轉換，兩種格式並存於資料表**），owner 裁定「先假設到萬位數」⇒ 7 字元。舊格式的編號查得到，只是一眼看不完，這個代價是那次裁定接受的。
  - 釘住這件事的是 `visual-guards/replies-filter-panel.ct.spec.tsx` 的「整個 id 要看得見、而欄位不得比它明顯寬」，兩個方向都會紅。
- **預設**：狀態勾好五個非終局值（尚未執行、進行中、等我回覆、等待外部、轉派中），
  負責人與類型都空。**因此預設畫面本身就是一個篩選**——把狀態那一軸的勾全部取消，終局狀態才會一起進來。
- `轉派中` 不是狀態而是鎖：任務 `lock === "reassigning"` 且未終局時也會被這一格撈到。

### 3.2 兩個區塊
- **未結束 · N** —— 依優先權（高 → 中 → 低 → 凍結）再依建立時間新到舊。
- **已結束 · N** —— 可展開，**預設收合**；依結案時間新到舊。終局＝已完成／終止／重複。
  有 `#tasks/<id>` 錨點時自動展開。

**兩個空狀態**：完全沒有任務時是「目前沒有任務」；有任務但篩掉光了是「沒有符合篩選條件的任務」。

### 3.3 任務卡（`TaskCard`）
整張卡可點開合（預設收合）。**收合時就看得到**的東西：

- **卡頭一行**：**狀態圖示**（狀態色的線條圖示：尚未執行＝虛線圓、進行中＝圓內播放、等我回覆＝帶「?」的對話泡泡、
  等待外部＝沙漏、可結案＝旗子、已完成＝圓內打勾、終止＝圓內叉、重複＝複製；名稱在 hover 提示與無障礙名稱裡。
  點了開狀態選單，選單第一行寫出目前狀態名稱，下面是查看等我回覆卡／查看等待外部節點／標記重複／終止／強制結案；
  結案後標記重複、終止、強制結案 disabled；標記重複用搜尋框以編號或標題搜全部任務來挑原票）、
  任務編號（點一下複製）、**優先權**（未結案時是下拉：高／中／低／凍結）、`轉派中` 鎖徽章（有才畫）。
  狀態只用這個圖示表達：卡片外框與進度條不隨狀態變色。
- **標題**（唯讀）。
- **常駐欄位**：`負責人`（＋傳訊息、＋**轉派…**）、`到期日`、`前任`（被轉派過才有）、`識別鍵`（是網址就變可點連結）。
- **展開整張卡時才畫的欄位**：緊接在 `到期日` 下面，同樣的標籤／值樣式：
  `類型`（帶齒輪，點進該類型的設定；沒有手冊時是「自由代辦」）、`產物`（有才畫，顯示個數，點了開 popover；
  `.md` 產物在全幅閱讀時一樣可以寫註解送給負責人）、`建立者`（與負責人相同時整列隱藏）。
- **依賴列**：`等 <taskNo>` ＋ 依賴任務的狀態與標題，可點進去。
- **進度列**：進度條 ＋ `步驟 N/M` ＋ 右端的時間膠囊（沙漏＋單一單位，完整的 `已歷時 <時長>` 在 title／無障礙名稱；結案後凍住）。
- **訊息輸入框**（未指派時 disabled；負責人已離開 —— 離職正職或已釋出外包 —— 時整個不畫，建議回覆也不畫）。

**展開後**才畫兩個同樣外框的區塊（白底細棕框、上方淡棕標題列：圖示、標題、右側摘要、收合箭頭；點標題列收合／展開
該區塊、不會開合整張卡，展開與否只記在畫面上）：**任務描述**（Markdown，空的話是「尚未填寫敘述」；標題列只有圖示、「任務描述」與箭頭，不寫行數（owner：「任務卡片點開的任務區塊，不用顯示有幾行」）；
預設只顯示約六行、底部淡出，下面「展開全文 ⌄」／「收起 ⌃」，放得下的描述沒有淡出也沒有按鈕），以及**工作流程**時間軸
（預設展開；標題列摘要展開時「N 個步驟 · 完成數/總數 完成」，收合時只剩標題列、摘要「完成數/總數 完成 · 進行中：<步驟名>」）——
一步一列：時間軸上是步驟的狀態圖示，步驟框依狀態上淡色；框內是步驟名與右側的耗時膠囊、DoD、備註（可開全螢幕閱讀）、等待外部的理由，審批步驟在框的右上角有琥珀色盾牌（需要你核可），
以及**內嵌的請示卡**（步驟綁著回覆卡時）。並行步驟包在「同時進行 · N 項並行」的區塊裡。

⚠️ 還沒有步驟時分四種說法，各自不同：載入失敗／載入中／`等待指派`（未指派）／
`等待 <負責人> 建立 Steps`。

### 3.4 深連結
- `#tasks/<id>` —— 覆蓋全部三個篩選，只顯示那一張（並自動展開已結束區）。
  **找不到時錨點留著**，畫面答「沒有符合篩選條件的任務」，出口是**常駐的編號欄位**——清空再按 Enter（它連同 hash 一起還原）。
  舊行為是靜默把 hash 復原回 `#tasks`，owner 2026-09-05（`rc-428906235337`）裁定改掉：一條指向不存在的連結
  與一條根本沒在篩選的連結在畫面上長得一模一樣。
  ⚠️ **「找不到」與「載不到」是兩句話**：只有 server 回答了（那個編號沒有符合的任務）才算找不到；讀取失敗（500、離線）
  畫面顯示「無法確認是否存在」而不是空狀態 —— 對一個沒能問出口的問題不得給答案。
- `#tasks/executor/<memberId>` —— 一次性種子：把負責人篩選設成那一位、清掉類型、狀態回預設，
  然後把 hash 正規化回 `#tasks`。

## 4. 監控（Monitor）

`MonitorPage`，一頁三區塊（即時遙測資訊）。

### 4.1 帳號資訊（Accounts）
每帳號一張卡；空狀態「尚無帳號用量資料」。
- 狀態點、**帳號名**（可就地改名）、`· 機器名`、右側 **估計 $花費**、**帳號詳情** modal
  （歸戶 key、帳號識別碼、組織 UUID、Email、組織、**回報標籤原文**、使用機器）
- **5 小時窗**：`· 用量 X% · 時間 Y%` ＋ 進度條（填色＝用量、標記線＝時間進度）
- **7 天窗**：同上；用量燒太快標 **`· 過熱`**
- 每個用量數字旁標 **`量於 X 前`**；沒有戳記時誠實留白。
- **已達上限**（`limit_reached`，附重置時間）：`已達上限 · 今天 HH:mm 重置`（明天寫「明天」，更晚寫 `M/D HH:mm`，非今年加年份），到重置時間或同帳號有成員之後呼叫成功就消失。

> 比較「用量 %」與「時間流逝 %」，燒太快就示警（Claude 訂閱用量窗口）。
> ⚠️ **過熱只在「還在回報」的帳號上判定**：用量百分比是上次回報的快照、時間百分比卻是即時算的，
> 拿沒人更新的數字去比還在走的時鐘，紅點會變成時間的函數。沒有人回報時就不判定（數字照留）。

### 4.2 機器資訊（Machines）
表格，一列一台機器。**欄位（`monitor.machineCol`）**：
**機器** ｜ **Claude** ｜ **Codex** ｜ 🖥 CPU ｜ 🎚 RAM ｜ 🔌 電源 ｜ **磁碟**

⚠️ **更早的版本這裡寫的是「機器 ｜ 帳號 ｜ CPU ｜ RAM ｜ 電量 ｜ 電源」**，那是 M1 的欄位：
帳號那一欄早就拆成 Claude／Codex 兩欄。後來加過一欄**操作**（⚙），已經拿掉，操作併進機器名稱的選單。

- **機器**欄由左到右：線上／離線圓點 → 機器名稱 ▾ → （未生效時）驚嘆號。機器 id 在名稱選單的「詳情」裡。
- 機器名稱是這一列的操作選單（跟 Claude／Codex 版本號選單同一個元件）：**改名稱**、**安裝／重新安裝 warden**、
  **拆除（uninstall）**、**刪除機器**。改名稱讓名稱就地變成輸入框；其他三件各自有自己的確認與結果 modal
  （拆除是 danger 兩段確認）。離線機器不能拆除、站台自己那台不能刪除，項目照樣列出但不能按。名稱旁沒有鉛筆。
- **磁碟**是 OffiCraft 在那台機器上用掉的磁碟總量，點開看分項（`MonitoringMachineDTO.disk_usage.categories`，伺服器排好的順序）：資料庫、資料庫自動備份、成員 workspace（底下前 5 位成員＋其餘合計）、日誌、升級殘留（舊版程式與舊資料庫副本）、其他；資料庫不在 OffiCraft 目錄時另有「舊資料庫副本」。升級殘留、舊資料庫副本、其他三項名稱後面有 ⓘ 說明裝什麼（前兩項不會自動刪除）；不認得的項目照 key 原樣顯示、用中性色。Claude／Codex 對話紀錄不量。從沒量過寫「尚未量測」。只量測，不刪任何東西。
- 機器欄以外的六欄各有自己的基本寬：CPU／RAM／電源／磁碟固定，Claude／Codex 平常 150px，整張表有一格放不下時那一欄依最寬的那格撐寬，每一列一致；框較寬時再各加上同一份多出來的寬度（見下一條）。版本太舊、未登入、過期這類標記排在值的同一行、不折行。
- **機器**欄寬＝最寬那一格的圓點、名稱與標記排成一行所需，但有上限；名稱比上限長就在欄內折行（▾ 跟著最後一個字）。改名稱的輸入框打開時，機器欄至少有一個固定寬度（不夠的部分暫時從其他六欄拿），關掉就還回去。框比表格需要的寬時，多出來的寬度平均分給機器欄以外的六欄，表格填滿框、名稱後面不留一大段空白。
- 表格比框寬時在框內左右捲動，**機器**欄固定在左；右邊還有欄位時框的右緣有陰影。表格最小寬讓機器欄的圓點、名稱與標記不被截斷。手機寬度改成一台一張卡，不捲動，卡片裡沒有「操作」那一行。

### 6.1 系統更新與備份
麵包屑 `設定 › 系統更新與備份`。
- **目前版本**、MCP 目錄雜湊等 build 身分資訊
- 若已最新：「✓ 已經是最新版」；若有新版：「有可用的新版本」＋ **升級到最新版**；更新檢查從未成功過（`/api/version` 沒有 `update_checked_ok_at`）時是中性的「尚未確認最新版本」，不說已是最新
- **接收 Beta 版本**（更新檢查納入 GitHub prerelease）
- **自動更新**（偵測到新版本就在背景升級並重啟；「升級完伺服器會自己重啟」留在名稱底下）·**新安裝的站台預設開啟**（首次用啟用碼設定密碼時寫入，只在正式版的程式寫；只升級到正式版）；已在使用的站台維持原本設定；從原始碼安裝（版本 0.0.0）維持關閉
- **更新檢查間隔**（分鐘，1–60，預設 5；wire 上是 `updater_check_interval_secs` 秒數）
- **讓助理告訴我新版本的功能**（`updater_announce_features`，預設開啟）·站台跑上正式版後（升級過去，或正在跑的版本被升為正式版），系統在下一次更新檢查時把該版 release 說明裡的 `## Announcement for station owners` 段（舊說明的「給站長的新功能公告」也認得）以一則 `system` 聊天訊息交給助理轉告 Owner（一次最多五版、新到舊，其餘只列數量並附 GitHub releases 列表連結）；關閉期間的公告不補發（有開接收 Beta 版本的站台例外：再打開後的下一次更新檢查會轉告關閉期間跑上的正式版）
- 備份健康
- **簽章金鑰**（T-62）— 目前有幾把、各自何時產生、哪一把在簽；「產生新金鑰」（不登出任何人、不必重啟）與「移除」（撤銷，無復原，連同該金鑰簽過的分享連結一起失效；確認框必須講出這個代價與「warden 憑證不會自己過期」）。T-80 起，機器換金鑰這件事會自己收斂（伺服器觀察每台用的是哪一把、看到舊的就請它自己去換），移除的判準因此從「都重新連過了嗎」變成可數的「每一台都已經換到新金鑰了嗎」；**這個數字目前只在機器清單的 API 資料裡（`token_key_id` / `token_key_current`），還沒有做進畫面。**
- 不重複顯示組織名稱

### 6.2 全域情境
麵包屑 `設定 › 全域情境`。整塊就是事件程序文件（T-a241 之前它是「角色誌」裡面的區塊 1）。

- 依 owner 的讀法分組（**上線（BOOT）／下線（STOP）／任務事件（TASK）**三組），每份一列，
  **不顯示 .md 檔名**。一列是圖示、名稱、ⓘ（只有使用者語言、系統互動、任務轉派 · 給接手人、使用者自訂四列有：名稱看不出這份文件是什麼或給誰讀）、狀態標籤（「可編輯」，或唯讀文件的「不能編輯」）
  與箭頭；沒有副標。列的讀名是名稱加標籤，不含 ⓘ。**份數與分組不寫在這裡**：`spec/openapi.json` 的 `BootDocKind` enum 是答案，
  而前端的列表是一張以它為索引的 `Record<BootDocKind, …>`，少一列編譯不過。
- 一般一列 = 一份文件：點進 → `BootDocPage`：檢視 markdown；**編輯** → 編輯模式，模式內有版本歷史，
  **同步預設內容在版本清單的「預設內容」那一列**（不是頁面上的並列按鈕；出廠 seed 不被覆蓋，永遠拿得回來）。
- **每一份的唯讀區都畫在編輯框上方**，看得到、改不動，編輯中也不收起來（owner 要對著它寫下半）。
  它不是唯讀文件的專利，也不是一個灰掉的輸入框：wire 上根本沒有欄位可以送它。
- **整份唯讀的那條路**：一樣點得進去、看得到全文，但沒有編輯器、沒有還原、沒有版本紀錄。
  `read_only` 由 server 回答；清單列標「不能編輯」所需的那一份副本
  （`BOOT_DOC_ROWS` 的 `readOnly`）由 `mock.boot-doc-registry.test.ts` 釘在共用表上。
  〈名詞對照表〉走這條路：它由前端字典產生，只隨新版本改變，開發者模式也解不開。開頭一句英文說明
  使用者寫到表中的中文畫面名稱時指的是同列的英文名詞，接著是對照表。
- **一種 kind 服務多份時**（今天只有〈啟動步驟〉：Claude／Codex 各一份，兩份不能互換所以不能合併），
  那一列點進去是**索引頁**（`boot`），再點一列才進 `BootDocPage`（`bootRuntime`）。
- **最上面兩列不受開發者模式影響**，依開機組裝順序：〈使用者語言〉在前、〈使用者自訂〉在後
  （owner：「可以改的放使用者自訂」）。
  - 〈使用者語言〉是一份 boot 文件，點進直接是它的 `BootDocPage`。沒改過時，它的預設跟著顯示語言
    （中文 → 中文預設；英文或未設定 → 英文預設）；改過就一律用改過的內容。存成（或還原成）與任一份預設
    相同的文字（去頭尾空白後比）就回到預設，重新跟著顯示語言。
  - **使用者自訂**走較早的另一套機制：點進 → 詳情頁；**重置**＝清空
    （回到未撰寫的 `預設` 空塊；boot context 組裝時空塊整塊跳過）。
- **開發者模式**（設定 › 進階設定）關著時，其餘文件都鎖住：列上沒有「可編輯」標籤，
  文件頁沒有編輯按鈕。鎖不鎖由 server 的 `developer_mode_required` 回答。

### 6.4 任務手冊

### 6.5 一般設定與進階設定
麵包屑 `設定 › 一般設定`／`設定 › 進階設定`。owner 可調的 server 旋鈕分兩頁（owner 裁定）：
**一般設定只有四格建議回覆與快到期提醒**，其餘全部在進階設定，依畫面順序。需要說明的列（單位、範圍、生效時機）說明在名稱後的 ⓘ 裡，登入有效期與四格建議回覆沒有 ⓘ；
後果留在名稱底下：轉派交接逾時秒數「逾時沒更新任務的外包前任會被回收」、機器憑證壽命「錯過換新的機器要重新安裝」、
Secret 請示卡的等待取得時間「時間到還沒取得，內容就會刪除，這張卡失效」、取得後保留時間「時間一到就刪除；填 0 是第一次取得當下就刪除」、
成員傳承字數上限「放不下的整筆不會被讀到」、傳承標題／內容字數上限「超過的寫入會被拒絕」、
備份保留份數「超過的會在下一次備份時永久刪除」。

進階設定：

| 參數 | key |
|---|---|
| 登入有效期 | `sessionTtl` |
| 成員登入有效期 | `agentTokenTtl` |
| Claude 第一次通知 / Claude 最後通牒 | `notice` / `handover` |
| Codex 第一次通知 / Codex 最後通牒回合 | `codexNotice` / `codexHandover` |
| 加速停止秒數 | `acceleratedGrace` |
| 轉派交接逾時秒數 | `reassignHandoverTimeout` |
| 機器憑證壽命 | `wardenCredentialLifetime` |
| 登入檢查間隔 | `runtimeLoginCheckInterval` |
| 未登入時重查間隔 | `runtimeLoginRecheckInterval` |
| 監控刷新間隔 | `monitoringRefresh` |
| **三個文件字數上限** | `docCapCharsDuty` / `Insight` / `ManualSop` |
| 喚醒聊天字數預算 | `chatBudget` |
| 備份保留份數 | `backupRetain` |
| 開發者模式 | `developerMode` |

一般設定：

| 參數 | key |
|---|---|
| 請示卡建議回覆 | `suggestedRepliesReplyCard` |
| 任務訊息建議回覆 | `suggestedRepliesTaskMessage` |
| 傳承訊息建議回覆 | `suggestedRepliesLoreMessage` |

⚠️ **五個字數上限是五個獨立的格子**（`DOC_CAP_ORDER`），不是一個共用值；
喚醒聊天字數預算與備份保留份數刻意**不在**那張表裡（單位與上下限都不同，各走各的 commit）。
四份建議回覆也不在那張表裡，而且是**一個訊息框一格、不是共用一格**（owner 裁定：任務跟請示卡要是不同的參數設定；T-33 依同一條裁定加上傳承那一格，聊天室那一格是所有成員共用）：
DB 四個 key（`suggested_replies.reply_card` / `suggested_replies.task_message` / `suggested_replies.lore_message` / `suggested_replies.chat`）、wire 四個平的頂層欄位，
所以「只改其中一份」是一次寫入，不是對一個共用 blob 的 read-modify-write。清單為空是合法值。
存是一格一份，顯示不一定只讀一格：請示卡回覆框（聊天內嵌、請示頁、任務卡內嵌三處相同）依序列卡片所屬任務類型（`card.task.type_key`）的任務手冊建議回覆（`GET /api/task-manual-suggested-replies`，owner 專屬，在任務手冊頁編輯）、開卡成員（`card.from`）的成員專屬建議回覆（`GET /api/chat/suggested-replies`）、`suggestedRepliesReplyCard`，相同文字只顯示在第一次出現的位置；卡片沒有任務、任務是自由代辦（`type_key` 為空）、開卡的是 owner 或名冊上沒有的 id，或某一份沒有句子時，那一份就不列。任務卡訊息框依序列任務類型（`task.type_key`）的任務手冊建議回覆、`suggestedRepliesTaskMessage`；外包成員的聊天室依序列它綁定任務的類型（worker DTO 的 `task_type_key`）的任務手冊建議回覆、成員專屬建議回覆、`suggestedRepliesChat`。正職聊天室不列任務手冊那份（同時可能負責多種類型的任務），已釋出外包的聊天室輸入框鎖住、不列任何句子；自由代辦一樣不列。刪除任務手冊時它的建議回覆在同一交易刪除；內建手冊同步預設內容不動它。
每個參數的意義與範圍見 [docs/guide/settings.md](../guide/settings.md)。

- **開發者模式**（表格最後一列）：`developer_mode`，預設關閉。關著時全域情境裡除了使用者語言與使用者自訂以外的文件都鎖住（見 §6.2）；Owner 與 admin 特助都能切換

### 6.6 主題
麵包屑 `設定 › 主題`。標題下兩個分頁：**外觀**（預設）選畫面上用哪套主題，**主題庫**做主題**管理**
（新增／編輯／匯入／匯出／刪除；列不能點選套用）。頭像下拉的偏好設定只顯示現在是哪一套（owner 2026-11-05）。
一套主題管得到：**顏色**（含不透明度與跟隨）、**用詞**（可覆蓋介面字，連英文標籤也能換）、
**字型**（安全白名單，內文／標題各一）、**頭像**（正職／外包／CEO／助理各一張）、
**工作室 Logo**、**導覽圖示**（七個主導覽頁籤各一張）、**外框背景圖**（平鋪／貼邊／滿版）。
外觀分頁由上而下：**依時段切換** 開關（server `display_theme_schedule`）——開著時是 2～6 列「開始時間 ＋ 縮圖 ＋ 主題」
與今天的時段細條，依觀看者當地時間到點直接換，應景主題期間仍顯示應景主題；關著時同一位置是 **主題** 選單（選了立刻套用，
縮圖同上）；再來是 **背景動畫**（自動／播放／靜止，只存在這台裝置的瀏覽器，不送 server）；最後是 **顯示應景主題** 開關（server `display_seasonal_theme`）。
玩法見 [docs/guide/theme.md](../guide/theme.md)。

  - **兩步驟驗證（MFA）** → 子頁（QR 掃碼啟用／停用）
  - **通行密鑰** → 子頁（清單、新增、刪除）
  - 三個子頁的返回鍵都回到帳號安全子清單
- 分隔線
- **登出**（紅色）

- **主題（Theme）** 只顯示現在是哪一套（依時段切換時寫「依時段切換（現在是 …）」，應景主題蓋過時寫應景主題），加一句指向 設定 › 主題
