> **owner(Seth) 2026-08-20 定案、2026-08-22 補三則裁定。** 本文件是「送到 agent 眼前的每一句話，都要住在 owner 編輯得動的文本裡」這件事的 **logical spec**：文件怎麼組裝、怎麼切、變數怎麼跑、寫入面擋什麼、還原出廠是什麼。程式與本文不合時 flag owner 定奪。

## WHY — 要解決的根本問題

owner 讀遍座艙上的〈下線程序〉（**T-6f44 之後那份文件在畫面上叫〈停止〉**；這一段保留當時的名字，因為它記的是那天發生的事），找不到 `restart_self` 這個字。那個字在**包住那份文件的那一行 Go 字串**裡：文件他改得動，夾住文件的句子他改不動、也看不到。同一個形狀在 lifecycle 的每一類事件上重複出現。

他的裁定（逐字）：

> 「唯一需要 hardcode 的是變動的數值⋯⋯剩下的訊息應該全部回到可編輯的文本中」
> 「第一行說明可以是固定的不能修改的**也會顯示在 UI 上**，因為有變數的部分通常就是說明發生什麼了，我們會需要修改的通常是接下來他應該採取什麼步驟」

⇒ **碼裡只留算出來的值**（死線的時刻、context 百分比、任務編號）；**那些值出現的句子本身也是文件的一部分**，只是放在一個 owner 看得到、誰都改不動的格子裡。

## 一、一份文件是什麼

一份文件由一個 **`kind` ＋ `key`** 定址。`kind` 是這份文件的種類，也是它在版本紀錄裡的系列名；`key` 是同一種類裡的哪一份。多數種類只服務一個 key；服務多個的種類，是因為那些文件**真的不一樣**（只有 codex 那份〈啟動步驟〉多一步「把控制權交回 sidecar」，其後的步驟編號整份位移；送錯那一份，agent 不會報錯，它只是永遠開不完機）。

所有種類寫在**一張表**（`bootDocRegistry`）。每一列回答這個種類的全部問題：有哪些 key、每個 key 的出廠種子檔是哪個、cap 從哪個設定讀、拒絕訊息怎麼稱呼它、允許哪些變數、要不要切唯讀區、渲染時兩半怎麼接、以及**是不是唯讀**。

> 🔴 **為什麼是一張表而不是一堆 switch。** 這是量過的：上一次新增一種文件，要改**六個檔案裡八個各自維護的 switch 與清單**，其中**四個完全沒有閘**——少寫一臂會編譯過、回 200、然後顯示錯的文字或什麼都不顯示。從一個 slice 解析出來的種類，不可能「在解析那一面存在、在版本紀錄那一面不存在」。

## 二、組裝：種子 ⊕ 覆蓋

每一份文件都有兩層：

- **出廠種子**：編進 binary 的 `seeds/*.md`。**永遠不會被寫入面改到。**
- **覆蓋（overlay）**：owner 的編輯，存在 DB。

讀取時折疊：有覆蓋就給覆蓋，沒有就給種子。回應同時帶兩個**回答不同問題**的旗標——`is_default`（有沒有人編輯過）與 `has_seed`（有沒有出廠版可以回去）。前者說你手上這份是不是原廠，後者是「還原出廠」這個動作的前提。

種子永遠不被覆寫，是「還原出廠」能成立的唯一理由：那條路不依賴任何編輯器可能弄壞的東西。

## 三、切法：唯讀區與本體

文件內文裡可以有**一行 marker**。marker 以上是**唯讀區**，以下是**本體**。

| | 唯讀區 | 本體 |
|---|---|---|
| 說什麼 | 發生什麼事 | 接下來要做什麼 |
| 誰寫的 | 程式（送出時填值） | owner |
| 可以有變數嗎 | 可以 | **一個都不行** |
| 改得動嗎 | 改不動 | 改得動 |
| 看得到嗎 | **看得到** | 看得到 |

**為什麼是文件裡的一行**：owner 要**看到**他改不動的那一半，而且要看到**模板原文**（含變數名）——這張票之所以存在，就是因為他去文件裡找一個字而那個字不在文件裡。marker 是**存下來的位元組**怎麼分半，這一點沒有改過：唯讀區從哪裡結束，答案只在種子的那一行。

⚠️ **這一段以前的結論句是「而且對 wire 契約零成本」，那一句已經被裁掉。** owner 2026-08-23：「唯讀區應該無法回寫，讀取有這個 key，回寫沒有這個 key，沒有人有任何方式可以回寫」。這一裁的意思正是 **wire 契約要付這個成本**：讀取面同時給 `text`（整份）、`read_only_head`、`body`；寫入面只收 `body`，伺服器自己把種子的唯讀區接回去。差別不是「多一道檢查」，是**送不出來**取代了**送錯被擋**——沒有欄位可以裝唯讀區，就沒有「回傳得對不對」這個問題。座艙那一邊：唯讀區渲染在編輯框**上方**，看得到、選得到、改不動。

marker 是一個**完全相等的整行**，不是模糊比對。模糊的邊界（「任何一行破折號」）會讓 owner 不小心造出第二道牆，而他的編輯被擋在哪裡會跟著默默移動。

**讀者看不到 marker**：送出前一律走渲染，marker 消失，兩半用**這份文件自己的接法**接起來。接法是逐份的、而且不是裝飾：今天的送出端真的有兩種形狀（〈加速停止〉與〈任務收尾〉用單一換行把本體貼在句子底下、其餘任務通知在兩半之間空一行，因為本體另起一塊：清單，或引言加清單）。把它們統一渲染，會**默默改掉**其中一種文件送到 agent 眼前的樣子。

⚠️ **「通常」不是「總是」。** 有些文件的變數落在指示句的**中間或尾巴**，對它們而言「唯讀區是前綴」與「本體零變數」不可能同時成立，除非移動位元組——而移動位元組是內容改動。這種文件**整份不切**，並且把衝突留給 owner 裁，不由執行者猜。猜的失敗模式是事後沒有人看得出來的那一種：文件讀起來很順，但它不再說原本說的話。

## 四、變數：宣告、驗證、渲染

一個名字會經過三道：

1. **宣告** — 每個種類列出它可以用哪些名字。
2. **驗證** — 寫入面拒絕任何沒宣告的名字（**宣告了零個名字的種類整個退出這一道**，見本節最後一段；那不是「一個都不准」）。
3. **渲染** — 送出時，宣告了卻沒有值的名字**讓送出失敗**，不會代換成空字串。

語法是 `{名字}`。

三道各自擋掉一種失敗，而在這套機制之前，**三種失敗都沒有任何地方會紅**：這棵樹先前對 owner 可編輯的文件**完全沒有插值也沒有驗證**，一份用了程式不會填的名字的文件，會帶著大括號原封送到 agent 眼前，而任何一個介面都不會吭一聲。

**沒有值時拒絕、而不是填空白**，理由是失敗的方向：帶著 `{task_no}` 的句子看起來就是壞的；被「修好」成空字串的句子**讀起來完全正常，只是指到錯的東西**。

**沒有宣告 ≠ 宣告為空**。前者是這個種類**完全不驗證**（owner 編輯的內文可能引用 JSON 範例，這個語法分不出它和變數的差別，為了替新文件加閘而弄壞今天在跑的文件，是划不來的交換）；後者是驗證、且一個都不准。

## 五、寫入面擋什麼

寫入是**本體的整份取代**，不是追加，也**碰不到唯讀區**（見 §三的裁定）。每一道閘都說「什麼都沒寫進去」——因為 owner 的編輯框裡有一整篇東西，他需要知道要不要重打：

| 擋什麼 | 回什麼 | 為什麼 |
|---|---|---|
| **唯讀文件** | 405 | 這份文件顯示是為了讓人看見 agent 被告知什麼，**沒有任何 principal 能改它**。所以講的是「這份文件是什麼」，不是「你缺什麼權限」——講權限會害讀者去找一個不存在的角色開通。 |
| **本體出現變數** | 400 | 本體是 owner 打字的地方；那裡的名字沒有人填。⚠️ **只對「有宣告變數」的那些種類成立**：宣告了零個變數的種類（〈系統互動〉的本體可能被 owner 寫進 JSON，`{name}` 這個語法跟一個例子分不開）整個退出這道檢查，大括號會照字面存下去、也照字面送到每一個 agent 眼前。這不是網子，不要當成網子寫進任何一句對外文案。 |
| **超過 cap** | 400 | 回應要告訴你：你寫了多少、上限多少、現在存著多少。 |
| **清空** | 400 | owner 裁定（`rc-a2dab0f20eea`）：清空就拒絕，並明說沒寫進去。**「清空＝還原出廠」是他明確沒選的那條，不得偷偷實作。** 代價他知情：要讓某一類事件不發通知，得另外做一個明講的開關，不能拿清空當靜音。 |

⚠️ **這張表以前有第五列：「動到唯讀區（含把 marker 整行拿掉）→ 400」。** 它不是被放寬，是**沒有東西可以擋了**：wire 上沒有那個欄位，所以那件事不是一個會被拒絕的請求，而是一句說不出口的話。想知道它為什麼變成結構性的，看 §三。

🔴 **兩道閘量的不是同一個東西，而且各自量的都是它問句裡的那個東西。**

- **清空**問的是「這次寫入有沒有把 owner 放得進去的東西清光」，所以量**本體**。改成量存下來的整份會**順手廢掉這道閘**：唯讀區在每一次寫入之後都還在，於是再也不會有「整份變空」這回事，而剛把自己那一半全刪掉的人會被告訴「沒有東西被清空」。（帶 `allow_shrink` 的清空之後，存下來的是唯讀區加分隔線、底下空白；唯讀區從來就不是他清得掉的東西，回頭的路仍然是一次還原出廠。）
- **cap** 問的是「**存下來**的那份文件有沒有超過天花板」，所以量接好之後的整份。那正是 `size_chars` 報的數字、座艙拿去跟 `cap_chars` 比的數字、拒絕訊息引用的數字；在這裡改量本體，會讓這三個數字對同一份文件講出三種話，而 owner 會在畫面說還有空間的長度上被拒絕。

cap 是**逐份**的，而且有些文件共用同一個設定——回應裡那個數字永遠是**即將判你這一次寫入**的那個。

🔴 **還原（restore）跑上面哪幾道，逐格寫出來。** 它是一個寫入面，但它不是從編輯框來的，所以不是每一道都適用；把「它也是寫入面」當成「它跑一模一樣的閘」，正是這一包之前那個洞的形狀。

| 這一道 | 還原跑不跑 | 為什麼 |
|---|---|---|
| 唯讀文件（405） | **跑**，而且在最前面 | 沒有任何 principal 改得動它，繞側面進來也一樣。 |
| 唯讀區 | **不是閘，是結構** | 還原走跟取代同一個接頭，把出廠的唯讀區接回去。所以一個 pre-marker 的舊版本被還原之後，回到現行列的是「出廠唯讀區 ⊕ 那一版的本體」。 |
| 本體出現變數（400） | **跑**，同一條規則 | 同一個函式，兩個呼叫端。 |
| 超過 cap（400） | **跑** | 更舊、更大的版本也是一次寫入；讓歷史把文件走回天花板之上，天花板就只是建議。 |
| 清空（400） | **刻意不跑** | 清空問的是一個還原沒有的意圖。還原一個空版本，是 owner 在清單上挑一個他看得見的版本。 |

## 六、還原出廠

還原是把覆蓋**做成墓碑**，讓折疊掉回種子。它是冪等的。

**這條路不套用任何長度上限**：出廠文字是產品的一部分，沒有任何設定可以擋住回去的路。這正是它作為**復原路徑**的意義——當一次壞的編輯已經讓 agent 開不了機時，這條路必須只靠座艙就走得通，路徑上不需要任何活著的 agent、也不需要任何 MCP client。

被丟掉的那份覆蓋會留在版本紀錄裡，所以**還原本身也是可以還原的**。

沒有出廠版的文件（`has_seed=false`）在這條路上是 404：沒有東西可以回去，這是誠實的「這裡沒有」，不是一個要繞過去的洞。

## 七、版本紀錄

每一次寫入（取代與還原都算）都把被換掉的那一版留進版本紀錄，用同一組 `kind`／`key` 定址。**沒有改變任何東西的儲存不留版本。**

版本紀錄的還原**也是一個寫入面**，而且是唯一一個**繞側面**碰到文件的：它不從編輯框來，它直接把一個舊版本裝回覆蓋列。

⚠️ **這一節以前寫的是「只住在取代那支函式裡的閘，是這條路走得過去的閘」，那句話現在是過去式，而且它描述的正是這一包負責關掉的洞。** 當時是真的：還原只跑 cap，內容規則完全不經過，所以它是唯一一條還能把**沒有唯讀區的舊版本**重新裝回現行列的路——它不發明那個形狀（沒有東西發明得出來），它是**重新強化器（re-armer）**，一次點擊就能把一個別處已經造不出來的危害重新上膛。

**現在的實際狀況**（權威是碼，這裡只是說得出口的版本）：還原取版本的**可編輯半**，走**跟取代同一個接頭**把出廠的唯讀區接回去，然後跑**跟取代同一條本體規則**，再跑 cap。唯讀文件在更前面就被擋掉。所以：

- **接頭與內容規則不再是兩份**——是同一個函式被兩個面呼叫，一個轉成 400，一個包成錯誤。
- **今天還原唯一不跑的閘是「清空」，而且是刻意的**：清空問的是一個意圖（「我要把這份清掉」），而還原是 owner 在版本清單上挑一個他看得見的版本，那個意圖不在。這件事寫在這裡，是因為「有一道閘它不跑」只要沒有人寫下來，下一個讀者就會假設兩條路完全一樣。

**不要在這裡寫「第幾個寫入面」。** 那個數字漂過至少兩次（曾經寫「第三個」，而同期的 commit message 寫「第五條」，兩邊都各自算了不同的東西）。要知道有幾條，去數 `putBootDocumentOn` 的呼叫端。

## 八、誰讀得到、誰改得動

- **讀**：機器層。agent 本來就在讀這些文件（開機折疊就把它們交到它手上），所以這裡沒有任何新東西給它。
- **寫與還原出廠**：助理層（owner 或 admin 助理）。這些文字會落進**每一個** agent 的開機脈絡、或是它被收走時收到的那一則通知；壞掉的那一份是所有人都讀到、而沒有人會回報的——**開不了機的 agent 不會在那裡告訴你它開不了機**。

**每一份文件的授權底線都一樣**，沒有任何一份跟別份不同。這就是端點做成泛型的理由：一組 `{kind}/{key}` 路由服務全部，而不是每份三個具名端點——後者的代價是每個 agent 的工具清單永久膨脹，為的是多數 agent 一輩子不會碰的文件。

⚠️ **唯讀不是授權底線的一格**。沒有任何 principal 過得了它，把它寫成路由上的 `requires` 等於宣告一個沒有人擁有的階級。它住在寫入路徑上，那裡才說得出「這份文件是什麼」。

## 九、送出端

文件是**送出端去讀**的，不是 agent 自己回頭抓的。送出端的責任有三件：

1. 取**渲染過**的文字（marker 不能到 agent 眼前）。
2. 供齊這份文件宣告的每一個變數的值。
3. 選對**哪一份**文件——事件的哪一個變體，就是哪一份文件，沒有第二個開關。下線那一對是這條規則最貴的一格：軟性走〈停止〉，硬性走〈加速停止〉，而只有後者的唯讀區帶 `{deadline}` 槽。

   ⚠️ **這一格的代價在 T-6f44 之後變重了，不是變輕。** 上一版的理由是「〈下線程序〉§1 教 agent 用『有沒有具體時刻』判斷軟硬」——**那條嗅探規則已經被拿掉了**（owner 的決定 5：不要再用字串比對另一份文件的第一行）。現在每一份自己講明它是哪一種，所以送錯不再是「少一個暗示」，而是**一句直白的假話**：〈停止〉開頭逐字寫著「這類停止沒有收尾倒數」，而時鐘正在跑。

🔴 **渲染不出來就不要送。** 這一條在接線那一包翻了方向，值得寫下來：以前唯讀區那一句是送出端自己在 Go 裡組的，所以文件讀不到只是少了檢查清單，句子還在——「降級不要靜默」。現在句子**就是**文件的唯讀區，沒有句子可送的情況有**三種**，一種都不能漏：

1. **文件讀不到**（fold 失敗）。
2. **宣告了的變數沒給值**——`RenderDocVars` 拒絕，這是送出端自己的 bug。
3. **這個 kind 宣告了 `Split`，存下來的文字卻沒有分隔線。** 這一種最晚才被抓到，因為它不像前兩種會自己報錯：`DocRendered` 對沒有 marker 的文字是原樣回傳，於是送出端會把「只有本體、沒有唯讀區」的殘篇當成完整通知送出去。

三種一律**整則不送**（怎麼「不送」四條臂並不一樣，也不是每條臂都有網接著——下一段逐條講，不要從這一句推），不要把還帶著大括號的原文推出去：`你的結束時刻是 {deadline}。` 讀起來像一個真的時刻，只是誰也解不開，比沒有通知更糟。

🔴 **而第 3 種比前兩種還危險，因為它送出去的是「非空」。** 前兩種回空字串，殘篇不是。不過**四條臂並不是同一個理由**，不要用一句話涵蓋——今天只有一條臂有網：

- **member delta 那條（下線／回收）有網。** client 端 `offboardFallback` 在「這則通知沒帶到那份文件」時會自己喊一聲，而它是靠**空**來啟動的：殘篇非空，網就不啟動，於是既沒有正確的通知、也沒有那句提醒。最貴的一格也在這條臂上——`{deadline}` 只存在於唯讀區，切掉之後 agent 拿到的通知通篇沒有任何時刻，而時鐘正在跑。⚠️ **T-6f44 之後這裡更難堪**：〈加速停止〉的本體要 agent「在指定的結束時刻前停止」，而那個時刻只寫在被切掉的唯讀區——本體會叫 agent 趕一個它看不到的時刻。（上一版寫的是「〈下線程序〉§1 教它把沒有具體時刻讀成軟性」，那條規則已經不存在。）
- **context-high band 與任務那兩條 chat row 沒有網。** 那三條臂上，殘篇與空字串同樣無聲，所以「保住 fallback」在這裡不是理由。**理由是殘篇會誤導。** 例：〈轉派程序（前任）〉的本體寫著「請停止推進並完成必要收尾……」，而**是哪一張任務只寫在唯讀區**——切掉之後，手上有多張任務的前任會不知道要停哪一張，可能停錯。（這條臂還有後備：接手人那則訊息是另外組的，仍然會送出，並要他主動 `post_chat` 找前任。）

一句話：**有網的那條臂，非空會讓網不啟動；沒網的那兩類，理由是殘篇會誤導。** 兩邊的結論都是不送，但寫下來的理由要各自成立。

**進得來的路是一列比分隔線還舊的覆蓋。** `docBodyMarker` 是分割那一包才進種子的，**沒有任何 migration** 改寫當時已經在資料庫裡的覆蓋列——分割上線前編輯過這些文件的安裝，手上就是這個形狀。今天**沒有任何東西造得出這個形狀**：寫入面連一個裝唯讀區的欄位都沒有，種子的唯讀區是伺服器自己接上去的，所以「沒有唯讀區的文件」不是一個會被拒絕的請求，而是一句說不出口的話。

⚠️ **這一段以前寫到寫入面就停了，而那樣寫是漏掉了一扇門。** 讀起來像「沒有人放得回去」，但有一條路可以：**還原（restore）不是產生器，它是重新強化器（re-armer）**——它從來不發明這個形狀，但在 T-3201 之前，它能把版本紀錄裡一個 pre-marker 的版本直接裝回現行列、不經過任何內容閘，再寫成一筆新的歷史；也就是說，一個沒有別的東西造得出來的危害，owner 按一下就能重新上膛。現在它走**同一條存檔路徑**（同一個接頭、同一條本體規則），所以它裝回去的東西身上帶著出廠的唯讀區。剩下的只有那些**已經存在資料庫裡**的列，而它們要到有人寫它們的那一刻才會被碰到（而那一刻，寫入面會順手把唯讀區補回去，把它修好）。

⚠️ **通知類嚴格，開機折疊寬鬆，這個不對稱是刻意的，不要「順手」把它抹平。** 判定住在知道 `spec.Split` 的那一層（`eventNoticeText`），不住在 `DocRendered`——後者只收 text 和 join，根本不知道那個 kind 宣告了什麼。開機折疊必須留著寬鬆的那一支：開機文件的唯讀區是**標題行**，讀者少了標題照樣開得起來；把 fold 也改成拒絕，會把**一列過期的覆蓋變成 agent 開不了機**，比這個洞嚴重得多。這道籬笆有測試守著——`TestSystemInteractionText_AMarkerLessOverlayStillBoots`——把嚴格推到開機那條路，會在那裡紅。

同理也不放在 `foldBootDocDTO`：座艙必須還看得見這種文件，owner 才修得動它。在讀面拒絕，等於把一份壞掉的文件同時變成不可讀**也不可修**。

## 取代了什麼，以及還沒取代什麼

在這套機制之前：這些句子是 Go 字串相加；座艙上沒有入口；沒有插值、沒有驗證；同一句話要改就得改碼，而改碼的人不是 owner。

✅ **機制與送出端今天已經對齊：十份全部接上。** T-3201 接了九份（開機折疊的那幾份、下線那一對〈停止〉與〈加速停止〉、任務事件裡的〈轉派程序（前任）〉與〈解除阻擋〉，以及 owner 裁掉重複的交接備註之後（`rc-0c36d8739b8f`）切開並接線的兩份〈接手程序〉），**最後一份〈任務收尾〉由 T-7870 補上**。（今天的十份不是當時那十份：〈新任務〉已在 T-239 移除，〈你手上的任務可以結案了〉是之後才加的。）

🔴 **那一份為什麼會落單，值得留著當教訓。** 它當初的具名理由是「`decideTaskCloseNudge` 是一個沒有 server 可以折疊覆蓋的純函式」——**那句話對函式成立，對路徑不成立**：`closeTask` 是 method，而且就在呼叫它的前兩行已經在用 `s` 讀任務手冊。於是它在 T-3201 期間**文件存在、可編輯、有版本紀錄，而沒有任何送出端在讀它**——owner 存檔會拿到 200、會多一筆版本紀錄，agent 收到的字卻一個位元組都不會變，且**沒有任何介面說得出這件事**。更難察覺的是它的唯讀區帶著變數佔位，**長得就是一副已接好等著被 render 的樣子**。

⚠️ **它也吞掉過一次已核可的修正**：owner 在 `rc-812aa13fb165` 逐句核准的改寫寫進了文件，卻從未送達任何 agent，直到 T-7870 接線那一刻才第一次真的送出去。**同形的事在〈解除阻擋〉身上也發生過一次**（文件改成三分支、送出端照送舊單句、而測試全綠），那次由 `bd07821c` 修好。⇒ **「文件改了」與「agent 收到了」是兩個獨立的事實，測試綠不能證明第二個。**

**這個危險的形狀值得記住，即使今天已經沒有未接線的文件**：一份沒接線的文件，owner 編輯會拿到 200、會多一筆版本紀錄，而 agent 收到的字沒有變，**沒有任何介面告訴他**。⇒ 日後**新增**任何一份事件程序時，「文件建好了」與「送出端在讀它」是兩件要分別坐實的事；只做前者，這一節描述的狀態就會重演。

⚠️ **這個危險已經真的發生過兩次，都留著當證據。**〈解除阻擋〉的三分支本體是 owner 批准的改寫（`rc-8c0045ef7c38`），落進了種子、拿到了版本紀錄，而 `releaseDependentsOnClose` 照舊送它自己那句舊的單句——測試還是全綠的，因為當時沒有任何一條測試去問 server「你實際送出去的是什麼」（`bd07821c` 修好）。〈任務收尾〉是第二次，形狀一模一樣，由 T-7870 修好。
